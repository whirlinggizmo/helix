Build the game in `{DIR}/spec.md` in Haxe, using **raylib 5.5's API**.

- **How raylib looks here.** This is raylib 5.5 in Haxe. Each raylib header is a class in package `helix.raylib`: `raylib.h` is `helix.raylib.Raylib`, and `import helix.raylib.Raylib.*;` brings its functions, constants and colors in unqualified, as raylib names them. `raymath.h` is `Raymath`, `rlgl.h` is `Rlgl`, `raygui.h` is `Raygui`, and the examples' `rlights.h` is `Rlights`. raylib's structs are classes of the same names and fields in `helix.raylib`. Write it as you would write a raylib game.
- **Extras.** helix-raylib adds calls raylib hasn't, in `helix.raylib.extras`, each module imported apart (`import helix.raylib.extras.Models.*;`). Their doc comments are in `{DIR}/docs/extras/`, a page for each, listed in its README.md, and a small program using each in `{DIR}/docs/extras/examples/`: read the ones you need, and use what helps.
- **Docs:** raylib 5.5's own headers are in `{DIR}/docs/include/` and its C examples in `{DIR}/docs/examples/`. Read them, and `{DIR}/docs/extras/`, as you need. Read nothing else about the library: no library sources, no other documentation, no web. Where it differs from raylib in C, the compiler tells you.
- **Assets:** the game's files are in `{DIR}/assets/`. The program names them by their paths from this directory, as `"assets/characters/Adventurer_Body.glb"`.
- **Building and running:** in `{DIR}`, `node run.cjs [arguments]` builds the program and runs it, passing it the arguments (as `--enemies=50 --seed=1`, each `--name` or `--name=value`). It runs in a page in a headless browser of its own, 1280 x 720, with no sound, as that build takes seconds where the native build takes most of a minute. A compile error is printed and nothing runs. What the program logs is printed, and a screenshot it saves with raylib's call for it is saved in `{DIR}` under its file's name: look at them to see the game. The run ends when the program does, after `CloseWindow`, or after 60 seconds, so give the program a way to stop (an argument naming the frames to run, say). What the game saves stays from one run to the next. Build and run as often as you like.
- **One program.** The game is a desktop program, and the page is only the quicker way to build and run it: helix-raylib runs the same code in both, and each run checks that the native build compiles too. Write it as a desktop raylib program, with nothing for the page or for one target: no `#if js`, no emscripten calls, no `js` or `cpp` package. You may add to `build.hxml`.
- **Natively, at the end:** when the game is done, `haxe build.hxml` builds it natively as `native/Main`. Run it once with `./native/Main [arguments]` from `{DIR}`, to check it there: it runs on a display of its own, never on the desktop, with no sound, and your shell waits for it to exit.
- **Touch:** the display here has no touch screen, so the touch controls can't be tried. Write them as the spec says.
- **Writing:** write to `{DIR}` only: the game's `.hx` files (`Main.hx` and what it imports), its shaders, and `build.hxml`, then `NOTES.md` with each compile error you hit, in order, and what you changed for it; each place raylib's API and the extras had no call for what the spec asks and what you did instead; each place you were left guessing and what you guessed, the extras' calls among them; and anything you expect not to work.
- **Budget:** stop at 3 hours or when the spec is met, whichever comes first, and reply with one line saying which.
