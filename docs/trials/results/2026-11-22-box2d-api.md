# API trial: helix-box2d's draft (2026-11-22)

Whether agents who know Box2D's C API can write a program against helix-box2d's draft API from its types and doc comments alone:
Box2D 3.2 under its C names in Haxe, not built yet. Six fresh Sonnet agents in two rounds of three, each a `claude -p` in a directory
of its own outside any repository, in the blind trials' sandbox (`run_entrant.py --trial`), compiling for JavaScript against the
draft's sources (`-cp docs/api`) and helix-math, round 1 at `e8c86964` and round 2 at `4f20d8db`. Each was given the draft brief
made for Box2D, the draft's sources and README, and a task naming no call: a floor and a tilted ramp, a stack of boxes and bouncing
balls, a one-sided terrain built from its own points, a kinematic platform moved back and forth, a trigger zone printing what
enters and leaves, a door hinged to the ground turned by a limited motor, a cart on two sprung wheels with a driven rear wheel, an
impulse at 2 seconds, each ball's hard hits printed, every moving body's pose read into one buffer each step without allocating, a
ray cast down each second printing the point, normal and body hit, and at the end the bodies awake, each ball, the door's angle, the
cart's x and the world's state hash. The draft changed between rounds as below. The inputs were made outside the repository beside
the runs.

## What it found

| finding | what changed |
|---|---|
| Whether a reused `out` allocates nothing, and whether an event struct's arrays are reused (3 of 3, round 1) | `Box2D` says an `out` is filled in place and an array a call fills reuses its elements and grows as needed, so a step's reads allocate nothing when each is passed the same one, and every `out` says it is filled in place. Round 2: 3 of 3 reused their `out`s; 2 of 3 still asked whether an event array grows, which round 2's change answers |
| Whether a def's nested structs exist (`def.base.localFrameA`, `shapeDef.material`) (2 of 3, round 1) | `Box2D` and each def's constructor say the structs a def holds are made with it. Round 2: none asked |
| A `B2Transform` made with no rotation read as zeros (2 of 3, round 1) | It turns nothing, as `B2Rot` made with no arguments does |
| Which side a chain collides on, and whether 3.2 still needs ghost points (3 of 3, round 1) | `B2ChainDef` says its front is to the right looking from each point to the next, points listed right to left make ground whose top is up, and `b2CreateChain` refuses an open chain whose ghost points are left at their defaults. Round 2: 3 of 3 listed them right to left with ghost points set |
| Whether `b2Body_SetTargetTransform`'s target is for the end of the step (2 of 3, round 1) | Its target is reached at the end of the next step |
| Whether a sensor's visitors need `enableSensorEvents` (1 of 3, round 1) | `isSensor`'s note says both shapes need it. Round 2: 3 of 3 set it |
| A motor speed's sign for a wheel rolling forward (3 of 3, both rounds) | The wheel and revolute joints' `motorSpeed` and their setters say positive turns body B counterclockwise relative to body A, a wheel rolling toward +x on level ground needing a negative speed |
| Comparing ids by `index1` alone (1 of 3, round 1) | nothing: each id's doc says to compare with `B2_ID_EQUALS`, and round 2's used it |
| A helper making a joint's frames from a world anchor, a typed `userData` (1 of 3 each, round 2) | nothing: Box2D 3.2 has neither, and helix-box2d keeps Box2D's C API |
| `Sys.println` in JavaScript (1 of 6) | nothing: Haxe's, not the library's |

Round 1's three programs and round 2's three compile against the final draft.
