# Shared platform contracts

Reusable contracts live in `src/helix/`. Shared game/rendering code calls them identically on both targets. Target launchers select named profiles, which run an app on its services (the static classes `Window`, `Input`, `Graphics` and the others); framework/game sources contain no target conditionals. No adapter traverses entities, implements game menus or constructs batches.

## Graphics

`IGraphics` is the GPU as a hardware abstraction layer: textures (2D, cube, data, render targets, depth arrays for shadows), stream and static buffers, programs built from a `ShaderSource` (both GLSL dialects and their bindings), pipelines made from a `PipelineDesc` (program, buffers' layout, primitive, indexing, blend, depth, culling and winding, depth-only, block 0's clip flip), passes (the screen's after any into targets and shadow maps) and one `draw`. Its doc comments are the contract. An adapter knows no program, layout or pipeline of HeliX's own: the framework's programs are generated from `src/helix/graphics/shaders/` (sokol-shdc compiles each; its `bare_yaml` reflection, checked against `shaders.json`, becomes a Haxe layout class with the program's `source()`, its `buffers()` and its packing constants), and `helix.graphics.Pipelines` describes, makes and keeps the framework's pipelines on each GPU. See [ARCHITECTURE.md](ARCHITECTURE.md).

Edges are smoothed by multisampling, asked for before the window opens: a profile's `run` takes a `WindowOptions`, whose `requestMsaaSamples(count)` asks for 1 (none), 2, 4 or 8 samples a pixel, 4 when not given. It's a request: natively the window gets what the driver grants, in the browser any count over 1 turns the canvas's `antialias` on and the browser chooses how many (nearly always 4). `IGraphics.msaaSamples` answers what was given, and `maxMsaaSamples` the most a window could ask for here (natively the GPU's most, at most 8; in the browser the count the canvas has when antialiased), for a settings menu to offer and apply at the next start. Render targets are drawn with the screen's samples and resolved into the texture sampled at the pass's end, so they're as smooth as the screen; shadow maps are depth only and single-sampled.

Vertices and records are little-endian float32, laid out as the generated layouts say. UVs refer to the top-to-bottom caller-provided image rows; neither backend silently flips pixels. Blend modes: opaque; alpha, SRC_ALPHA / ONE_MINUS_SRC_ALPHA for RGB and ONE / ONE_MINUS_SRC_ALPHA for alpha; additive, the source times its alpha plus what's there. Handles are context-local, positive and typed by the operation; they must not be retained after destruction. Adapters reject invalid dimensions, capacities, prefix lengths, handles, uniforms and draw ranges. Application data is trusted in-process memory, not an untrusted command stream. The first native backend is GL; Metal, Vulkan or WebGPU are new adapters of the same contract, behind a new executed gate.

## 3D

`helix.math.Random` is a seeded xorshift32 generator, an instance per stream, the same bits on every target (DECISIONS 118). `Interpolate` is the small math every game writes again (lerp, inverseLerp, remap, clamp, smoothStep, angles the short way round, moveToward, damp at a rate the same at any frame rate); `Curve` is a path through points (Catmull-Rom), by control points (Bézier) or straight between them, open or closed, in 2D or 3D, asked where it is at t, its tangent, its length and the t at a distance along it (DECISIONS 120). `helix.scene.Scenes` is a game's flow as a stack of `Scene`s (enter, update, draw, pause, resume, exit, as overrides the stack calls through the object): push pauses the one under, pop resumes it, replace swaps the top, each with an optional `Transition` (`Fade`) drawn over the frames and swapping the scenes at its middle; a scene with a `Loader` (its loads gathered with one progress) is shown the loading scene until they're done (the built-in `Loading`, another, or none); the built-in `Splash` holds until a press (`activated`) or its most wait, and `Loading` (a picture, a caption and a tip the game sets, or a loading scene a level brings) can hold once loaded for a press (`anyFramePressed`), the movie-like opening a game may use or not; the window losing focus pauses the game's clock and the top scene unless turned off; scenes read the stack's input, which an autopilot replaces; the run option `quick=1` skips every wait and transition, for development (DECISIONS 123, 124). `helix.collision` is 2D collision in floats, the same on every target: `Collide2D`'s overlaps of rectangles, circles and convex polygons (the separating axis theorem, with the least move apart), points inside them, segments and rays with where and the normal (`Hit2D`), sweeps, and a box moved and slid over a grid of solid tiles (`Move2D`, which sides met); `SpatialHash2D` narrows which pairs to test (DECISIONS 121). `helix.render3d` is right-handed with +y up; distances are world units, angles radians. `Camera3D` is a perspective or orthographic camera with GL clip depth, a node seeing from its world transform (`setView` places it at an eye looking at a target, relative to its parent, so one under a car rides along), and the same viewport and viewport-area model as `Camera2D`. `Mat4` is column-major, as shaders take it. Two modes, as the earlier frameworks had. Immediate: `Batch3D` draws triangles and lines (cubes, wire cubes, spheres, a grid) through the `Color3D` and `Lines3D` pipelines, shading solid shapes on the CPU by one directional light. Retained: a `Stage3D` holds a tree of `Node3D`s (a bare one a group) and the kinds on it (DECISIONS 130): `Model` (its `Part`s, each a `Mesh` and a `Material`), `DirectionalLight`, `PointLight` and `SpotLight`, `Camera3D`, `Sprite3D`, `Text3D` and `Particles3D`, each a class holding only its own data, under `helix.scene.Node` (a name, the flags, a parent and children, `find`) and draws them through `Lit3D`: world matrices by dirty flags, the first four lights (directional, point or spot; a stage starts with none and no ambient light), each model's box culled against the view, the opaque sorted by material and mesh and the see-through back to front, one instanced draw a run. Materials are glTF metallic-roughness (base color and texture, metallic, roughness, a normal map and its strength, emissive light, lit or not), shaded by glTF's BRDF, lit by an environment map as well where the stage has one, and tone mapped (Khronos PBR Neutral, ACES or none, after an exposure); generated meshes carry tangents for the normal map. Shadows are DECISIONS 78, environments 79. The node rules are in DECISIONS 61. `helix.render2d` has the same two modes in 2D (y down, angles clockwise on screen): `Batch2D` draws immediately (quads, sprites, shapes, nine-slices, emitters, and text with `drawText` and `drawTextWrapped`, measured and wrapped by its `Font2D`), and a `Stage2D` holds a tree of `Node2D`s (a bare one a group) and the kinds on it: `Sprite2D` (a texture or a region of it, sized, pivoted, tinted, a nine-slice frame), `Shape2D` (a rectangle, circle, line or polygon by its static constructors, filled or outlined, a rectangle's corners rounded), `Text2D` (a line or a wrapped block in a font) and `Particles2D`, drawn in tree order through a camera, culled by their bounds, any node clipping its children.

Models come from glTF 2.0 files (GLB, or `.gltf` with its buffers and images beside it) through `Models` (the runner's `ModelCache`), in Haxe on both targets: a `ModelFile` holds the file's meshes (a part a primitive), materials and node tree, and `instantiate()` makes a node tree sharing them, its lights its own: a `Model` for each node with a mesh (its primitives the model's parts), a light of its kind for each light node, a bare `Node3D` for any other; they are found once by their file names (`find`). What a file uses that isn't read yet is listed by `ModelFile.warnings`: morph targets (and their weights' animations), a second set of joints and weights, primitives other than triangles, metallic-roughness, occlusion and emissive textures, alphaMode MASK, texture transforms, a second texture coordinate set, and textures or images it can't find.

## Host, runner and services

`IHost` is the platform's host and nothing more: it runs the loop (`run(init, frame, cleanup)`), keeps the clock, owns the window, quits, and passes run options (the URL query in a browser, `HELIX_*` environment variables natively). The `Runner` is what a host pumps, the same on every platform: at init it builds the app's services over a profile's adapters (`Adapters`) and the engine's shared services over those, and binds the static classes the app reaches them by; each frame it polls the shared services and input, runs the app's frame, ends input's frame and measures the frame; at cleanup it closes the shared services, the app, audio, input, the framework's pipelines and the GPU, in that order. An app never closes a platform service itself.

An app gets the program's services as static classes (DECISIONS 130): `Graphics`, `Input`, the `Window` (with the drawing surface's size and pixel ratio, and focus: has the keyboard and is shown), `Screen` (the presentation, the app's design fitted to the window, DECISIONS 113), `Assets`, `Fetch`, `Storage`, `Audio` (sounds, over `AudioResources`), `Textures`, `Models` and `Environments` (over `TextureCache`, `ModelCache` and `EnvironmentCache`), `Screenshots` and `TestHarness`; `Time` (the host's time, the frame's elapsed and CPU time, and the game's clock) and `Host` (whether anything is still loading, `busy`, run options and quitting). Each forwards to the instance the runner binds (`instance`, null outside init and cleanup), its forwarders written by a build macro (`helix.macro.Facade`) from the service's interface or class with their doc comments, so the interface stays the adapters' and the tests' side. A run option (`Host.getOption`, with `getOptionBool`, `getOptionFloat` and `getOptionInt`) comes from the URL query or `HELIX_<NAME>`, else from `config.json` beside the program (`Config`, DECISIONS 125 and 131; beside the page on the web, which says whether it has one, beside the executable natively): read as the program starts, outside the asset cache, a `default` object with named profiles over it, the one in force named by the file's `profile` or the run option `config`, read by dotted names; the app is built once it has come. One program, one set: they're statics (`Window.title = ...`, DECISIONS 114 and 130), bound by the runner at init and cleared at cleanup, read from an app's `init` on (a profile builds the app, `() -> new App()`, once they're bound); the framework's own classes in `src/` take what they use rather than reading them, so they test apart with fakes (the scenes, which read `Input` and `Time.clock`, and a test binds those). `IApp.frame(dt)` gets the frame's measured seconds, held between 1e-6 and 0.1 (`FrameClock`); `Time.frameElapsed` is the unheld time. The game's time is `Time.clock` (`helix.time.Clock`, DECISIONS 119): the frames' time scaled and paused as a whole, updated before each frame, with a held delta for animation and an unheld elapsed time for a `Ticker` (`helix.time`, fixed-rate steps that see input's tick edges); `Timers` (after, every) and `helix.tween.Tweens` (a value from one number to another by an `Ease`, with a delay, repeats and yoyo) run on its delta, so they pause and slow with the game. The runner calls the app through the object each time, so after a hot reload its new methods are what run. `Host.canQuit` is true natively and false in a browser, whose `quit()` stops the frames without closing the tab.

Input's focus policy is shared (below); an input adapter only reports focus: the window's focus and the page's visibility in a browser, sokol's focus events natively. Web Audio unlocks on the page's first key or pointer press and suspends while the page is blurred or hidden. `ITestHarness.publish` hands a check its result (`window.result` in a browser; a JSON line on stdout and the `HELIX_RESULT` file natively).

## UI

`helix.ui` makes widgets of nodes, read each frame, with focus by keys and pads. A `Ui` over a Stage2D, its camera, a `Pointer` looking at that stage and the input makes widgets (`label`, `panel`, `button`, `toggle`, `slider`, `progress`, `list`, `textField`, `tile`: a picture with a caption, selected by the game, its picture able to come later; `colorPicker`: a `0xRRGGBBAA` `color` chosen on a square of saturation and brightness, a hue bar and an optional alpha bar, shown in a swatch and typed as hex in a field of its own (`hexField`, RRGGBBAA or RRGGBB, with or without #, text naming no color marked `invalid` and changing nothing), its hue kept through greys and black), each owning its nodes and a layout `Box`; `update()` once a frame after the pointer's; the app then asks (`clicked`, `value`, `changed`, `selectedIndex`, `activated`, `submitted`), nothing is called back (DECISIONS 61). `Box` lays out rows, columns and stacks (anchors), sizes fixed, fitted, growing by weight or a share, with padding, gaps and alignment, writing nodes' positions (by their pivots) and sizes once a frame (`Box.arrange`). Arrows and the D-pad move focus to the nearest widget that way on screen (a grid moves in two dimensions), or with none that way in the order widgets were made, as Tab and Shift+Tab always do (Left and Right unless a slider or text field takes them; a list takes Up and Down; a color picker takes all four while a part is driven by them, Enter, Space or South stepping through its square, hue bar, alpha bar and none), Enter, Space or South activates, Escape or East is back; the ring shows only when keys or a pad moved focus; after keys or a pad something has focus; a key held into a new screen (`reset`) does nothing until let go; while a widget has the keys (`capturingKeys`, always for a text field) a game should leave them be. A `Panel` holds its widgets (`add`), hidden with it, its background a rectangle or a nine-slice frame. The `Theme` sets colors and sizes through its properties (`textColor`, `invalidTextColor`, `gap`, ...), among them `cornerRadius`, the radius rounding panels, buttons, fields, lists, tracks and bars (8 to start; 0 for square), which the focus ring follows. `Ui.press(name)` uses a widget by name as a click would, when it's shown and usable: tests and the autopilot's `click`. Beneath it: a `Shape2D` rectangle shaded from its `color` to its `endColor` across or down it (`shading`, `Batch2D.gradientRect`), `IGraphics.applyScissor`, Batch2D's nested clips and Stage2D nodes clipping their children (drawn and picked), nine-slice sprites, and wrapped text.

## Picking and the pointer

`Camera3D.computeRay(x, y, ray)` is the ray through a framebuffer pixel (from the top-left, as the pointer is) within the camera's viewport area, from its near plane, through the matrices the stage draws with (perspective or orthographic); false outside the viewport. `Stage3D.pick(camera, x, y, ?hit)` returns the nearest hit as a `PickHit` (the node, the distance from the near plane, the point in the world and in the node's own space, the normal facing back along the ray), or null; `pickAlong(ray, ?camera, ?hit)` follows any ray (sprites and text need the camera to face). Models are hit by their triangles from either side, after their world box (one beyond the nearest hit so far is skipped); a skinned model by its triangles as posed now, posed on the CPU with the GPU's blend; a see-through model (blended material or tint) only where its alpha reaches a half; 3D sprites and text by their quads as drawn (a text by its whole block), not yet by their texels; emitters never. `Stage2D.pick(camera, x, y)` returns the topmost node under a point by each kind's own area (a filled shape's area, a rounded rectangle's without the corners cut off, an outlined one's or a line's stroke, a sprite's rectangle, a text's block). Both honour the node flags: disabled skips the subtree, unpickable passes the node (its children still hit), hidden is still hit. Picks walk the tree as it is, so a gear swap changes the next pick.

`helix.scene.Pointer` is the pointer over stages, asked of, never telling the nodes (DECISIONS 61): stages are added in draw order with their cameras (`addStage3D`, `addStage2D`), `update()` once a frame after input picks them topmost first, and `isHovered`, `isPressed`, `isDown` (held, kept while dragged off), `isClicked` (released over what it was pressed on), `hit3D` and `captured` answer. A press on a 2D node captures the pointer until it's released: the stages under it see nothing. Edges last the frame they happen in; the pointer is sampled once a frame, so two clicks within a frame are one.

## Lights

A Stage3D considers the first 64 lights its walk finds (a hidden or disabled one isn't found). Each draw it scores every one against each drawn model's box: its brightness (luminance of color times intensity), times its falloff at the box's nearest point (inverse square from 0.1 out, windowed to nothing at its range; nothing past the range), times a spot's cone at the box's center (unless the light is inside the box); a directional light scores its brightness everywhere. The 16 with the best score over the drawn models are the table the shaders read; each model is lit by the 8 of those that reach it most, named in its instance record, so models sharing a mesh still draw as one. The first four lights that cast have shadows. A surface shader's `helix_light_count()` and `helix_light(i, …)` are the model's own lights, 0 to the count less one.

## Node flags

Every node, 3D and 2D, has three flags, each its own and on to start (but `pickable` for text, off until asked: a label lets picks through to what it's on): `enabled` (off: it and everything under it are skipped by drawing, picking and updates, an emitter under it not moved on; the only one reaching the children, whose own flags are kept), `visible` (off: its own output isn't drawn, a light doesn't shine or cast, an emitter still moves on; it stays placed and its children are as they are) and `pickable` (off: a pick's ray passes its own output; its children can still be hit). Drawing and picking don't depend on each other: hidden and pickable is a hit area.

## Skinning and animation

A glTF skin is read into a `Skin` (its joints by name, their inverse bind matrices) and each vertex's first four joints and weights (normalized to sum to 1; an unweighted vertex follows its first joint). Each copy of a file (`instantiate`) binds its skinned models to that copy's joints; `Model.bindSkeleton(skeleton)` binds a model to any skeleton with the same joint names, refusing (false, unchanged) one missing a joint, which is how gear from a file of its own goes on a character, and how it is swapped at run time. A skinned model's own placement doesn't move it (glTF's rule): its joints do. A socket is a node added under a joint (`character.find("Middle1.R").addChild(sword)`); it follows the joint like any child. Animations are read into `AnimationClip`s of `Track`s (translation, rotation, scale; linear, step and cubic spline), targeting nodes by name, so a file of animations alone (`clips`, `getClip("Walk")` finding "CharacterArmature|Walk") plays on any skeleton with those names. An `Animator(root)` plays one clip at a time on the nodes under root, refusing a clip that moves a node root hasn't, crossfading over the seconds `play` is given (a node only one clip moves blends with its rest pose, where it stood when first bound); a play during a fade starts from the clip playing, dropping the one fading out. `Stage3D` draws skinned models through the skinned programs: every skinned model's joints of a pass go into one data texture (inverse(model world) × joint world × inverse bind, three texels a joint), its first joint in its record, uploaded once a pass (the shadow pass and the draw). A skinned model is culled by its joints as posed, each padded by the farthest vertex it weights and the box by 2% (a rest-pose box drops a limb swung outside it), after the walk has posed every joint. A skinned model draws through its material's surface shader's skinned variant (the packer makes one for every surface shader, its vertex stage moving each vertex by its joints before the shader's vertex hook), and casts through that shader's skinned caster where it has one. Not yet: animation layers, morph targets, more than four joints a vertex. Checked: `AnimationTests` (sampling, weights, the Quaternius files, binding and refusal, crossfades and rest blending, joint matrices, a limb posed out of its rest box still drawn); the `animation` example in Chromium (clips, crossfades, the outfit swapped, the sword socket, posed shadows). `Models` loads a file once and shares it. Dressing a character from part files of their own is the game's (the dressing room's `Outfit`, DECISIONS 116), over three queries: `Node3D.collectModels` sorts a file's models into skinned and rigid (its own armature copy passed over), `bindSkeleton` binds a skinned one to the character's joints by name, and `Node3D.findAttachment` says where a rigid one hangs: the piece (the node under its nearest joint-named ancestor, as an importer may split a mesh) and the joint, which it keeps its offset from.

## Shaders and effects

A shader is an app's `.hxshader` asset (`Shaders.load`, its parameters by name in `ShaderParameters`) or one of the library's (`helix.shaders`), packed into the program at build time, a class whose fields are its parameters, each held to its range, colors `0xRRGGBBAA`. Its kind is the framework block it includes. A surface shader is a Stage3D material's (`Material.setShader`, or a library class made on the material: `Unlit`, `Toon`, `Dissolve`, `Water`), drawn on static and skinned models alike, its shadow following its vertex hook and its `discard`s; a material has one. `Dissolve` lays its noise over the model at rest in its own space (triplanar, `scale` its repeats per unit), so the holes stay on a skinned body as it animates. Every material's hit flash (`HitFlash`: `trigger(color, seconds)` fading over the stage's time, or `amount` held) and rim light (`Rim`) show whatever its shader. A model's passes (`Outline`, a width in world units; `Silhouette`, where something nearer hides it) stack with any shader, on and off by `enabled`. A screen effect (`ScreenEffect`; the library's `Bloom`, `Tonemap`, `Fxaa`, `Blur`, `Vignette`, `ColorLut`, `Crt`, `ChromaticAberration`, `Pixelate`) runs in a `PostProcess` chain (`add`, `remove`, in the order added, each on and off by `enabled`) over the scene drawn between `beginScene` and `endScene`, the last drawn by `present` into the screen's pass, the HUD after it, outside the chain. An effect that wants HDR (Bloom, Tonemap) makes the scene RGBA16F where the GPU draws half floats: its `Stage3D` then writes its light untone-mapped as sRGB values running past 1, its clear color comes out as given, and a `Tonemap` with the stage's mode follows the last effect wanting HDR unless the chain has its own; elsewhere the chain is 8-bit and Bloom thresholds the tone-mapped frame. A sprite effect (`SpriteEffect`; the library's `SpriteOutline`, `SpriteFlash`, `SpriteDissolve`, `PaletteSwap`) is a `Sprite2D`'s or a `Sprite3D`'s `effect`, or `Batch2D.effect` for what a batch draws next; one effect is shared by the sprites given it, its values read as the batch ends, and sprites drawn one after another with one effect and texture are one draw. The library's time-driven ones (a flash's fade) follow the stage's or batch's `time`, which an autopilot holds.

## Screenshots

`Screenshots.take(?name, ?done)` saves the next frame the app ends: the `Runner` calls `frameEnded` after the app's frame, which reads the frame back (`IGraphics.readPixels(0)`, before the frame is presented: a browser can't read it after), encodes it with the shared `Png` (row filters, then deflate with LZ77 and the fixed Huffman codes, the same bytes on every target) and hands it to `IExport`: a download in a browser, a file natively in `HELIX_EXPORT`, else the user's pictures directory (`XDG_PICTURES_DIR`, else `~/Pictures`) under the product's name, else `exports/` beside the program. Files are named `<product>-<date>-<time>-<n>.png` unless named. `readPixels` also reads a render target, for shots at another size or pixel checks. Encoding runs on the host thread, so a screenshot's frame is slower. Checked: a static example's screenshot matches the window pixel for pixel natively (an X11 grab) and in Chromium (a page capture), alpha 255 throughout; the encoder round-trips through Haxe's own inflater. The examples take one on F9 (`examples/shared/src/DevKeys.hx`); autopilot scripts with `{"op": "screenshot", "name": "title.png"}`. `Screenshots.sample(points, done, ?failed)` reads the same frame at a few points given in the design's units (`Screen`'s), each the pixel under it as `[r, g, b, a]`: the autopilot's `sample`, which `tools/example.py` compares between the browser and native within a tolerance (checks at a few points, not golden images). A sample can be required unlike an earlier one (`differsFrom`, `by`: an effect against it off) or like one (`matches`, `within`: what must look the same either way). Checked: the `shaders` example's samples alike in Chrome and natively under sokol, SDL3 and SDL_GPU (lavapipe), within 1 per channel, the frame the same way up on each; the `shader-gallery` example's 44 within 3 against sokol, SDL3 and SDL_GPU (Vulkan).

## Input

`IInput` exposes named physical keys (`isDown`, and the edges `isPressed`/`isReleased` per tick and `isFramePressed`/`isFrameReleased` per frame), mouse buttons with the same edges, one primary pointer (position, held, edges), the wheel, typed text, touches with a two-finger gesture (pan, pinch, twist), and four gamepad slots (`getPad`, and `isPadDown`/`isPadPressed`/`getPadAxis` over any connected pad). Tick edges are counted: `consume()` after a simulation tick takes one of each, so every press reaches exactly one tick and two presses between ticks reach two; frame edges, text, the wheel and lifted touches last one frame. Repeated keydown does not create another press. Focus loss lets go of everything held and drops pending presses, so nothing resumes by accident. Typed text is the characters after the keyboard layout, and comes only while text entry is on (`textEntry`; off at start): the UI turns it on while a text field has focus, a game typing on its own turns it on itself, and the router tells the input source, so SDL3's text input (and the keyboard a platform shows for it: a phone's, Windows' touch keyboard when a pad is plugged in) is only asked for then (DECISIONS 128). The browser shows no keyboard for it yet (a phone's needs a focused input element). There is no IME composition or rebinding service yet. `activated` says whether the user has pressed a key, a mouse button or a finger yet, the browser's user activation applied on every target (a pad's press doesn't count, as a browser can't unlock audio with one), so a title screen's "press any key" and the start of music are one flow everywhere (DECISIONS 122).

An input adapter is an `IInputSource`: it reports its platform's events as they are (keys, text, mouse buttons, moves and leaving, the wheel, fingers, focus, and each connected pad's state at poll) to the shared `InputRouter`, which the `Runner` owns and whose `InputState` is the app's `IInput`. The router holds the policy once for every platform: the primary pointer is the mouse with its left button or the first finger down, a second finger letting it go until all lift (so touch drives the pointer natively too); losing focus lets go of everything, and while unfocused presses, text, the wheel and pads are ignored (pads stay connected, released and centred); text is dropped while Control or Super is held; the first four connected pads fill the four slots in the platform's order. Key codes are each adapter's table (sokol's codes are `Key`'s GLFW numbers, its right-hand modifiers folded).

Browser maps `KeyboardEvent.code`, pointer events and every connected Gamepad API controller in the standard mapping. Native maps Sokol keyboard/pointer/touch events and up to four Linux evdev controllers (Sokol supplies no gamepad API), with fixes for known drivers (xpad's face buttons, a generic HID pad's right stick on Z/RZ, digital triggers); there is no mapping database, and the checks feed recorded evdev events through a pipe, not a physical controller. Sticks are clamped to [-1,1] and both triggers to 0..1. `Gamepad.getAxis` and `getPadAxis` apply a radial dead zone (`deadzone`); action thresholds are game policy (`Controls.hx`). Controller disconnect returns neutral state. Gamepad polling cannot preserve a physical press/release that happens entirely between samples; keyboard/pointer event edges can.

Pointer positions use top-left-origin **framebuffer pixels**, not CSS pixels. Browser converts client coordinates using the canvas rectangle and framebuffer size; native supplies Sokol coordinates. Shared `Menu` maps them through letterboxing to 960×720 design coordinates. Only a primary pointer is exposed; pointer support does not constitute multitouch flight/fire controls.

`InputState` is the shared accumulator the router feeds; autopilot and tests feed it directly. Autopilot supplies normal input to the same game/menu code and observes explicit app probes: keys held and pressed, widgets clicked by name, the pointer dragged between two points in the design's units (`drag`, through `Presentation.toPixelsX`), text typed (`type`), and the frame's pixels sampled. Its bounded JSON parsing uses `Reflect` for schema field checks, not shader or game-internal reflection. See [PACKAGING.md](PACKAGING.md).

## Audio

An **asset** is encoded source bytes identified by a path. An **audio resource** is reusable playback data. `AudioClip` holds fully decoded PCM; `AudioStream` holds a progressively decoded source. `AudioPlayback` is one playing or paused instance. Streaming describes delivery/decoding, not where the encoded source lives: a stream can use a stored file, a remote URL (a browser), or a download read as it arrives (natively). There is no separate audio player object or persistent spatial emitter in this slice.

Use shared `AudioResources.loadClip(path, loaded, ?failed)` or `loadStream(path, loaded, ?failed)` (the `Audio` static's): `loaded` gets the resource, `failed` the message (left out, the failure is logged with the path), and a cancelled request calls neither. These return an `IRequest`. A sound plays through a bus: `Audio.music.play(theme, true)`, a game's own (`Audio.addBus(name, parent)`), or `Audio.play(resource, loop, volume)` for the effects bus; each returns an independent `AudioPlayback` with `stop()`, `pause()`, `resume()`, `volume`, `pitch` (0.25 to 4), `pan` (-1 to 1), `fade(to, seconds, ?done, stopWhenSilent)`, `bus`, `heardVolume`, `state` and `finished`. A `Bus` has a `volume`, `muted`, `heardVolume` and `fade(to, seconds, ?done)`; fades are linear in decibels, a silent end taken as -60 dB. `Audio.crossfade(from, to, seconds, toVolume)` fades one out and stops it while the other fades up to toVolume (1 by default), both linear in power (`FadeCurve.Power`), so the two together keep their loudness through the middle. `Audio.saveBuses()` and `loadBuses()` keep every bus's volume and mute by name as JSON through `Storage` (key `audio`). `resource.release()` drops the caller's ownership once; active playbacks retain it until stopped or naturally finished. A released resource cannot start another playback. Pausing retains the resource and any source lease. The `Runner` polls natural completion and shuts down resources before the backend.

`loadClip` requires a successfully ensured encoded asset, then decodes it through the shared `AudioDecoding`: it sniffs the file (RIFF, `OggS`, an ID3 tag or an MPEG frame's sync bits), decodes a WAV itself with the shared `Wav` (mono PCM16 at 44100 Hz, at most four seconds), hands Ogg (Vorbis, Opus) and MP3 to the platform's `IAudioDecoder`, holds encoded files to 8 MiB and decoded clips to 2Mi frames, checks the PCM, and runs at most two decodes at once on a `Jobs` pool, each completing once on the host thread (`Decoded(samples)`, mono float32 PCM, `Failed(message)` or `Cancelled`). `loadStream` resolves usable storage first, then the host, and opens it with `IAudio.openStream`. Browser storage supplies a leased Blob URL; remote playback in a browser uses an audio element on the URL without storing the download (call `Assets.ensure` first to keep it). Natively (`IAudio.playsUrls` false) the remote file is downloaded, played while it arrives (`AudioLocation.Downloading`, a `GrowingSource`) and kept in the cache when the download ends, so the next play is local ([ARCHITECTURE.md](ARCHITECTURE.md), Audio). Service network counts prove each ensured WAV/Vorbis/Opus fixture downloads once across cache reads, clips, streams and a second process/page.

`IAudio` is the platform's output and nothing more: whether it exists (`available`) and runs now (`running`), clips copied from mono float32 PCM at 44100 Hz, streams opened from an `AudioLocation` (`openStream(source, done)` answers `Opened(id)` or `Failed(message)` on the host thread and returns an abort), voices started from either (`playClip`, `playStream`), stop/pause/setVolume/setPitch/setPan/isPlaying (volume and pan changes ramped by the adapter so a fade stepped once a frame doesn't click), destroying clips and streams (each stops its voices on both targets), poll and shutdown. Ids are the adapter's. `AudioPlayback` owns what is the same everywhere: a playback asked for before audio runs waits and starts at a later poll once it does (a browser runs audio from the page's first key or pointer press), volumes, pitches and pans are held to their ranges before they reach an adapter, its heard volume (its own times its bus's) is sent once a frame when it changed, and a voice of 0 (no free voice) or no output at all yields an already finished playback. The typed resource layer owns destruction; applications should not mix direct handle destruction with its lifetime methods.

In a browser, `WebAudioDecoderAdapter` decodes Ogg and MP3 with `decodeAudioData` on a 44100 Hz `OfflineAudioContext` (no user gesture needed; it resamples) from an owned copy of the bytes, and mixes the channels down. `WebAudioAdapter` is output only: its `AudioContext` is made on the first key or pointer press (browsers allow audio to start only in a gesture) and suspended while the page is blurred or hidden; clips play through buffer sources, streams through an `HTMLAudioElement`, each voice through a gain and a `StereoPannerNode`. Ogg/Vorbis and Ogg/Opus clips ran in Chromium in the service checks; MP3 is accepted the same way. This does not establish every browser's codec availability. Decoder rejection reports failure. Browser decoding is asynchronous, but the mixdown and copy run on the host thread and are not preemptible.

Natively, `audiodecoder/libsndfile` is a codec adapter of its own over a thin C **libsndfile 1.2.2** bridge (libsndfile reads MP3 through mpg123 from 1.1 on): `LibsndfileAudioDecoderAdapter` (the `IAudioDecoder`, decoding whole Ogg/Vorbis, Ogg/Opus and MP3 files on worker threads, handed back through the `Mailbox`) and `LibsndfilePcmFiles` (files read a part at a time for streaming, Ogg, MP3 and WAV). Mono/stereo sources with rates 8000–192000 Hz downmix and linearly resample to mono 44100 Hz in C; decoder PCM need not match browser PCM bit for bit. The limits bound returned PCM, not the internal allocations of a browser/library decoder. Logical cancellation delivers one terminal result and suppresses late completion; it cannot interrupt browser decoding or a native codec call already running.

`SokolAudioAdapter(files)` and `Sdl3AudioAdapter(files)` are the native outputs over one mutex-protected mixer in C with 32 clip slots, 16 mono voices mixed to stereo (equal-power pan; the mono sum on a one-channel output), device-rate resampling times each voice's pitch, and volume and pan ramped across each callback, and streams read through an `IPcmFiles` (the profile gives it `LibsndfilePcmFiles`). A stored stream is opened once on a worker to check it reads, a download on the host thread once 64 KiB have arrived (or the whole; again as that doubles while the codec can't open it yet); each voice opens the file again and its poll keeps it up to 88200 frames (2 s) ahead, 2048 frames a read, for up to 2 ms a frame, rewinding on loop. Underruns produce silence and keep the voice; the end finishes it after queued data drains. The pump stays in this adapter: it is how a push-based output plays a file as it's read, and an output fed from its own callback would read there instead. A second push-based output (SDL3's audio streams can be pushed to) would move the pump to shared code. The device mixer runs independently; a host stall beyond the queued audio (2 s when full; at 186 ms, a 300 ms stall was heard as a gap) interrupts a native stream, as the decoding is the frame thread's, not the audio thread's. A direct stored source is not subject to whole-file fetching's 8 MiB cap. Natively a stream plays any WAV libsndfile reads, while a WAV clip takes only the shared decoder's mono PCM16 at 44100 Hz.

Natively a download is decoded only while it has arrived 64 KiB past the codec's position (or is whole, or failed: then what came plays and the voice ends); the 2 s ring covers a slow connection's gaps, and a longer gap is heard as one. A remote stream needs a Content-Length to start before its end: without one it's answered once whole. libsndfile can't learn an Ogg file's length before its last bytes, so one opened early plays to the end of its stream, and an MP3 without a Xing or Info header opens only once whole (libsndfile scans it for its length). A download is held in memory while it plays (its whole length, and the codec's copy for each voice), up to 256 MiB, and has ten minutes to arrive. `tests/streaming` proves it natively under SDL3's dummy driver: a WAV served 32 KiB each 100 ms and an Ogg/Vorbis 4 KiB each 100 ms sound before the server sends their last byte, play to their ends and are kept; a body without a Content-Length is answered whole; a connection dropped halfway ends its voice and is logged. Browser remote fixture playback/cleanup passed, but the small fixtures do not prove a browser starts before network EOF. General WAV clip layouts remain a separate gate. MP3 clips and streams are accepted on both targets (the `audio-music` example opens its music as an MP3 stream), but no check covers MP3 yet: the service checks have no MP3 fixture.

The existing shared WAV clip decoder also has a stricter four-second PCM16 data limit; longer canonical WAV can use the stored stream path. Ogg and MP3 clips instead use the 2Mi-frame cap (about 47 seconds). These are current prototype limits, not a general audio library specification.

Asteroids now delivers eight quality 3 Vorbis files made from its original generated WAV sources using offline FFmpeg. It plays fully decoded clips. The revised thrust-v4 asset is a two-second circular noise/motor loop; shared game code applies a tick-based volume attack/release through the playback's volume. This is game policy, not a general sample-accurate fade API. Separate fixtures exercise WAV/Vorbis/Opus clips and streams, including stereo 48 kHz Opus input, malformed/empty files and decode cancellation. Real ALSA callbacks and PCM mixer assertions ran; checks do not establish audible output quality. Seeking, segments, spatial audio and richer playback-error reporting remain unfinished. SDK pin/license and the external native decoder dependency are recorded in BUILDING.md and dependencies.json; no decoder is shipped in browser Wasm.

## Assets

`AssetService` implements `IAssets` over the shared `FetchService` and `StorageService` (themselves over the platform's `IHttp` and `IStore`). `ensure(path, loaded, ?failed, ?progress, ?options)` returns `IRequest` and later calls `loaded` with the `Bytes` or `failed` with a message (left out, the failure is logged with the path); a cancelled request calls neither. It checks encoded storage first, fetches or reads packaged bytes on a miss, and reports success only after a committed storage write. Progress contains a phase (locating/downloading/storing/ready), received bytes and nullable total. `load(path, loaded, ?failed)` is ensure without progress or options. `streamSource(path, located, ?failed, download)` resolves a leased local source before a remote URL without ensuring it; with `download` (natively) it downloads instead of answering the URL, answers `Downloading` once the first part arrives with a Content-Length (whole without one), and keeps the file in the cache when it ends. Assets are source files; textures/clips/streams are runtime resources; playback/model placement are instances. A future glTF asset can produce mesh and texture resources without reversing that direction.

`IAssets.subscribe(path, target:IReloadable)` asks for `target.reloaded(path, bytes)` when that file changes and has loaded again; `unsubscribe` ends it. `AssetService.changed(path)` does the loading, past the HTTP cache (`FetchRequest.noCache`) and the stored copy, and stores the new copy; only `-D hotreload` browser builds call it, from hotreload-hx's changed-file notices. A failed reload keeps what subscribers have and is traced. `AudioResources` subscribes for its clips and swaps a reloaded clip's backend clip in place.

Paths reject schemes, absolute names, traversal and unsupported characters. Storage keys hash the asset base URL plus path; this separates hosts, but does not provide content versioning, integrity manifests or freshness validation. Browser uses IndexedDB encoded Blobs; native uses files with sibling temporary writes and replacement. Native packaged assets are under the executable's `assets/`; downloads are cached in `HELIX_CACHE` if set, else the user's cache directory for the program's identity (`$XDG_CACHE_HOME` or `~/.cache`, then company/product), else `cache/` beside the executable. This is a prototype cache, not a user-data sandbox or production platform cache-location policy. Storage quotas/errors fail explicitly; ensure does not silently bypass failed persistence.

## Fetch, storage, decoding and cancellation

`Fetch.fetch({url, ?maxBytes, ?timeoutSeconds, ?noCache}, callback, ?progress)` reports `Response({status,headers,bytes})`, `Failed(message)` or `Cancelled`. HTTP error statuses are responses; asset policy rejects non-2xx statuses. Defaults are 8 MiB and 15 seconds, the timeout covering the whole transfer on both targets. Headers are lowercase; the total is unknown for a compressed body. Progress runs at most once a frame. `StorageService` reads and writes whole files of at most 8 MiB by key (an asset path; the `Storage` static is the runner's cache); a read-only one (the packaged assets) refuses writes. `ImageDecoding` decodes images for textures and environments. All three, and `AudioDecoding`, run on `helix.core.Jobs`: at most two operations at once, each completing exactly once on the host thread at a later poll, cancelled ones (and those pending at shutdown) completing `Cancelled`, later ones refused with a failure.

Under them the platform contracts are operations (`IHttp.get`, `IStore`, `IImageDecoder.decode`) answering on the host thread, never during the call. Cancellation calls the platform's abort: a browser aborts its request; natively a transfer stops at its next part of the body (not while it connects), and a storage operation already running finishes on its own, its answer dropped. Cancellation doesn't undo a completed write. Delivery is cooperative (`WorkQueue`, nominally 2 ms a poll for each pool); it can't preempt a callback, decode or platform call. Whole downloads are assembled in memory; downloading straight into storage and resuming need a separate gate. Native HTTPS compiles but isn't yet an executed interoperability claim.

## Deferred scope

SDL3 is a candidate for a complete native platform adapter: graphics, window/input, gamepads and audio. Services can be selected independently, including mixed Sokol/SDL3 configurations; a second backend must preserve resource/lifetime/input/shader contracts and run the same tests. No SDL3 backend or matched SDL3 performance result exists yet. Desktop performance takes priority over executable size. A comparison must include shader generation and executed modern graphics, not infer behavior from available APIs.

Context/device recovery, modern native graphics APIs (Vulkan, Metal, D3D) and WebGPU remain graphics gates. Asset manifests/versioning/revalidation, eviction/quotas, concurrent ensure deduplication, large downloads, normalized HTTPS/redirect/deadline behavior, further codecs/playback controls, user-data storage, multitouch and text input remain service gates. Add operations for exercised needs; this remains a thin interface over actual adapters.

## Composition

Contract packages live under `helix.audio`, `helix.graphics`, `helix.input`, `helix.assets`, `helix.host` and `helix.debug`; `helix.core.Jobs` is the shared pool for asynchronous platform work and `helix.core.WorkQueue` supplies cooperative callbacks. Adapters live under `helix.adapters.<contract>.<api>`, named `<Api><Contract>Adapter` ([ARCHITECTURE.md](ARCHITECTURE.md)); their C sources, headers and extern bindings under the adapter's `internal/` directory, each extern bridge carrying the hxcpp build XML for its own C and libraries, so a profile links only the adapters it uses. A profile in `helix.profiles` picks a host and an adapter for each contract and runs an app on them through the `Runner`: `BrowserWebGL2Profile.run` (WebGL2, DOM, Web Audio, Fetch API, IndexedDB, the page's image decoder) and `NativeSokolGLProfile.run` (sokol on GL 4.1, sokol audio with libsndfile, evdev gamepads, haxe.Http, files, stb_image). The rule for what may live in an adapter, and its check, are in [ARCHITECTURE.md](ARCHITECTURE.md).
