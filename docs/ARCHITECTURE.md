# Architecture

HeliX is three layers, and code belongs to exactly one of them.

| Layer | Where | What it is |
| --- | --- | --- |
| Engine | `src/helix/` outside `adapters/` and `profiles/` | Everything that is the same on every platform: rendering (`render2d`, `render3d`, the framework's shaders and pipelines), assets, audio resources, input state, particles, math, the runner. Pure Haxe: no platform API, no target conditional. |
| Platform contracts | the interfaces the engine calls (below) | What a platform must provide, stated as capabilities, not as engine features. |
| Adapters | `src/helix/adapters/<contract>/<api>/` | One platform API behind one contract: a hardware and OS abstraction layer, nothing more. |

**Adapter directories are named for their contract:** `adapters/<contract>/<api>/`, where `<contract>` is the interface's name without the `I`, lowercase, words run together (`IAudioDecoder` → `audiodecoder/`, `IInputSource` → `inputsource/`), and `<api>` is the platform API it uses (`webgl2/`, `sokol/`, `dom/`). A contract whose object comes with another adapter's lives in that adapter's directory: `IWindow` in `host/` (the host makes the window; the native hosts share theirs, below), `IPcmFiles` in `audiodecoder/libsndfile/` (the native audio output streams through the codec). The `<api>` directory names the exact API, not the platform, so it says where an adapter can run (`http/fetchapi` runs wherever the Fetch API exists: browsers, Node, Bun, Deno); profiles are named for platforms. **The adapter class is `<Api><Contract>Adapter`**, with words the API's name ends with and the contract's starts with written once: `graphics/webgl2/WebGL2GraphicsAdapter`, `store/indexeddb/IndexedDbStoreAdapter`, `audio/webaudio/WebAudioAdapter` (not WebAudioAudio), `http/haxehttp/HaxeHttpAdapter`. Helpers beside it are named `<Api><Thing>` (`DomWindow`, `LibsndfilePcmFiles`). Native C, headers and extern bindings go in the adapter's `internal/`; what several adapters share, in `adapters/shared/`: the native hosts' `NativeHost` and `NativeWindow` over the C each host implements (`window.h`, and `surface.h`, the framebuffer the GL graphics adapter draws in), so `SokolHostAdapter` and `Sdl3HostAdapter` hold only how each opens its window, runs its loop and quits; and the native graphics adapters' `NativeGraphics` over the C each implements (`graphics.h`), so `SokolGraphicsAdapter` and `Sdl3GpuGraphicsAdapter` hold only their setup and how they build a program. Each adapter's extern bridge carries the hxcpp build XML for its own C and libraries, so a build compiles and links only the adapters its profile uses.

A **profile** (`src/helix/profiles/`) picks one adapter per contract for a target and hands them to the engine. It is named for the backend it draws with, a build's backend ([CONVENTIONS.md](CONVENTIONS.md#build)): `WebGL2Profile`, `SokolGLProfile`, `Sdl3GLProfile`, `Sdl3GpuProfile`; the examples' launcher for each is `examples/shared/launch/<backend>` (`webgl2`, `sokol-gl`, `sdl3-gl`, `sdl3-gpu`).

## The adapter rule

An adapter holds only what differs because of its platform or API.

- **In an adapter:** calls into the platform API; the API's quirks and limits worked around (GL's bottom-left origin, sokol's one write per image a frame, WebGL2's missing base instance); resource handles and their bookkeeping; the threads and callbacks the API needs, handed back to the host thread; validation that protects the platform (native memory, GL state).
- **Never in an adapter:** anything another adapter of the same contract would have to repeat. Formats the engine reads (WAV, glTF, .hdr), the framework's programs, vertex layouts and pipelines, policies (limits, queues, concurrency caps, caching, retries, lifetimes), state machines over the platform's events (edges, gestures, the frame's order), engine services and their wiring, test tooling.
- **The test:** if a second adapter for the same contract (WebGPU beside WebGL2, SDL3 beside sokol, another OS's file system) would have to copy a piece of code, that piece belongs in the engine, and the contract hands the adapter data instead.

### Enforced

`tools/check_adapters.py` runs first in `tools/check_types.py` and `helix.py test`, and fails on:

1. an adapter naming engine code (rendering, engine services, generated program classes or framework programs, shared decoders, the runner);
2. engine code using a platform API (`js.html`, `js.Browser`, `js.Syntax`, `js.lib`, `sys.`, `cpp.`) or a target conditional;
3. an adapter's C including a generated shader header;
4. two adapters of one contract sharing a run of six or more identical lines;
5. an adapter directory not named for a contract one of its adapters implements;
6. an adapter class not named `<Api><Contract>Adapter` as above.

What it can't see (the same logic written twice in different words, policy hiding in a contract's doc comment) is review's. The check has a list for known violations, each with the audit step that removes it ([ADAPTER_AUDIT.md](ADAPTER_AUDIT.md)); the audit emptied it, and it only shrinks.

## Contracts and adapters

As built today; what is still to change is under **Target shape** below.

| Contract | Adapters | Platform part (theirs) |
| --- | --- | --- |
| `IGraphics` | `graphics/webgl2` (browser), `graphics/sokol` + C (native, sokol_gfx on GL 4.1), `graphics/sdl3gpu` + C (native, SDL_GPU on Vulkan, Direct3D 12 or Metal) | Textures (2D, cube, data, render targets of RGBA8 or half floats with or without depth, depth arrays), buffers, programs built from a `ShaderSource`, pipelines made as a `PipelineDesc` says, passes, one draw, reading pixels back. |
| `IHost` | `host/dom` (browser), `host/sokol` + C (native) | The loop, the clock, the window, quitting, run options. The `Runner` (engine) is what it pumps; the app reads the services' static classes (`Window`, `Input`, `Graphics` and the others; engine), bound by the runner. |
| `IWindow` | `host/dom/DomWindow`, `host/sokol/SokolWindow` | The drawing surface (framebuffer size, pixel ratio), focus, title, sizes, position, fullscreen, displays and visibility where the platform has them. |
| `ITestHarness` | `testharness/dom` (browser), `testharness/stdio` (native) | Hands a check the program's result. |
| `IInputSource` | `inputsource/dom` (browser), `inputsource/sokol` + `inputsource/evdev` C (native) | Keyboard, text, mouse, wheel, touch and focus events as they arrive, each connected gamepad's state at poll, and the platform's key codes as a table. The shared `InputRouter` owns edges, the pointer, focus policy and pad slots; the app reads its `InputState` as `IInput`, and `Actions` (engine) reads named actions over any `IInput`, told by it as each tick and frame end (`IInput.watch`), so the autopilot's input drives them too. |
| `IAudio` | `audio/webaudio` (browser), `audio/sokol` + C and `audio/sdl3` + C (native, one shared mixer) | Output: clips copied from PCM, streams opened from a source, voices with a volume, a pitch and a pan, each change of volume or pan ramped across the output's next block; whether audio exists and runs now. Natively it streams through an `IPcmFiles` (the codec adapter's) and pumps its voices, as a push-based output must; `playsUrls` says whether it plays a remote URL itself (a browser) or is given the download (natively). The shared `AudioResources`, `AudioPlayback` and `Bus` own lifetimes, ranges, buses, fades and waiting for audio to start. |
| `IAudioDecoder` | `audiodecoder/webaudio` (browser), `audiodecoder/libsndfile` + C (native; also `IPcmFiles` for streaming) | A whole Ogg or MP3 file to mono float PCM at 44.1 kHz. The shared `AudioDecoding` owns sniffing, the WAV path, the limits, PCM checks and queuing. |
| `IHttp` | `http/fetchapi` (browser), `http/haxehttp` (native) | A GET whose response arrives in parts, and its abort. The shared `FetchService` owns limits, the timeout, progress, queuing, and the parts handed on as they come (a streamed download's). |
| `IStore` | `store/indexeddb` (browser), `store/filesystem` (native) | Files by key (read, write, remove, clear, lease). The shared `StorageService` owns key checks, the size limit, read-only refusal and queuing. |
| `IExport` | `export/download` (browser), `export/filesystem` (native) | Hands a finished file to the user: a download, or a file in the directory the profile chose (`HELIX_EXPORT`, else the user's pictures). The shared `ScreenshotService` reads the frame, encodes PNG (`Png`) and names the files. |
| `IImageDecoder` | `imagedecoder/canvas` (browser), `imagedecoder/stb` + C (native) | Bytes to RGBA. The shared `ImageDecoding` owns queuing, cancellation and shutdown. |

### Target shape (decided)

- **Host: done** (DECISIONS 81). Backend facts (`Adapters.info`) went with step 4: nothing read them.
- **Screenshots: done** (DECISIONS 86). `IGraphics.readPixels` reads the finished frame or a render target back; `Png` encodes in shared Haxe; `IExport` saves; `Screenshots` and the autopilot's `screenshot` command use them, in release builds too.
- **Asynchronous work: done** (DECISIONS 82). `helix.core.Jobs` is the shared pool (a queue, a cap, exactly-once completion on the host thread, cancellation with the platform's abort, shutdown); `FetchService`, `StorageService`, `ImageDecoding` and `AudioDecoding` run on it over `IHttp`, `IStore` and `IImageDecoder`; native adapters hand thread results back through `adapters/shared/Mailbox`. Left: one frame budget across the pools (each still delivers under its own 2 ms).
- **WebSockets, later:** a contract of their own (`IWebSocket`: open, send, receive, close), not folded into `IHttp`; a shared service on top for what's policy (reconnecting, queuing messages).
- **Audio: done** (DECISIONS 83).
- **Input: done** (DECISIONS 84).

## Input actions

A game's controls are named actions (`helix.input.Actions`), engine code over any `IInput`: a map from a name to its bindings (`Binding`: a key, a pair of keys, a pad button or a pair, a pad axis with a side and a threshold, a mouse button, a touch region), each giving -1 to 1, the action the binding pushed furthest across every pad. It asks the input it was given, never the adapter, and keeps its edges by being told as each tick and frame ends (`IInput.watch`, an `IInputWatcher`), so whatever plays an `IInput` (the autopilot's script, a test's scripted state) drives it with no call from the game. An action never bound reads as up, so a game's code runs before its bindings load. A touch region is an anchor on the visible area and an offset and size from it in the game's units, converted through the `Presentation` (`Screen`'s) as each finger is read, so it scales with what the game draws under a design size and keeps its physical size without one. A rebind (`capture`) takes the next key, pad button, axis past half way or finger once the frame it was asked in has ended (not the click on the Rebind button), Escape cancelling, and replaces the action's bindings of the same device kind (keyboard, pad, touch), leaving the others; the captured press reads as up until it is let go, so it doesn't also act. The bindings are saved as JSON under one Storage key beside the defaults the game bound in code, which `reset` restores; a saved action the game no longer binds is dropped. A binding to a UI widget, so the drawn button and the touched region are one, comes when the UI asks for it.

## Audio

The buses, the fades and the heard volumes are the engine's, worked out once a frame so both targets do the same arithmetic: `Bus` is plain data (`Audio.master`, `music`, `effects` from the program's start, a game's own from `Audio.addBus`), a playback's heard volume is its own times its bus's and the parents' up to the master (0 under a mute), and `AudioResources.poll(delta)`, which the runner calls with the frame clock's delta, steps the buses' and playbacks' fades (linear in decibels; a crossfade's two linear in power, so their sum holds its loudness) and sends each playback's heard volume by `setVolume` when it changed. Pitch (0.25 to 4) and pan (-1 to 1) are held to their ranges in `AudioPlayback`; the adapters take them as given. What is the adapter's is only how a change is heard without a click: Web Audio approaches a volume or pan by `setTargetAtTime` (10 ms) on each voice's gain and `StereoPannerNode`, its pitch the source's playback rate (a stream's media element with `preservesPitch` off); natively the one mixer (`adapters/shared/mixer.c`, under sokol_audio's output or SDL3's) mixes mono voices to stereo by equal power (left `cos((pan + 1)·π/4)`, right `sin`), the mono sum unpanned on a one-channel output, ramps each voice's volume and pan linearly across a callback from where the last ended, and multiplies a voice's resampling step by its pitch.

A remote stream plays natively while it downloads, and is kept, as a browser's element plays its URL. Where the output plays no URL (`IAudio.playsUrls` false), `AudioResources.loadStream` asks `IAssets.streamSource` to download: the asset service fetches the file as `ensure` would (a stale copy asked about, 304 leasing it), and, once its first part arrives with a 200 and a Content-Length, answers `AudioLocation.Downloading(source)`: a `GrowingSource`, the file's whole length taken at the start and each part written into it on the host thread as `FetchService` hands it on (`fetch`'s `part`), with `received`, `total`, `done` and `failure`. Without a Content-Length it answers once the file is whole. When the download ends the service keeps it in the cache under the asset's key, with its record, as any download (so `ensure` finds it current and the next play is local); one that fails after the answer ends its source and is logged with the path. The output's part is only reading it: `NativeAudio` opens a download through `IPcmFiles.openArriving` once 64 KiB have arrived (or the whole), again each time that doubles while the codec can't open it yet, and its pump decodes a voice only while the download is 64 KiB past the codec's `position` (or done, or failed), since the codec takes a short read for the end of the file; otherwise the voice waits on its 2 s ring. libsndfile's adapter copies the arrived bytes into C at each read (the codec's own allocation of the file's length, so nothing the garbage collector moves is read from C) and reads them through libsndfile's virtual I/O, which refuses a seek past what has arrived. Two of libsndfile's habits are that adapter's: it reads an Ogg file's last 64 KiB at open for the length, so an open before the end is shown none of them and plays to the end of the stream (rather than taking the last page arrived for the end); and it scans an MP3 without a Xing or Info header for its length, so such a file opens only once whole.

## Passes

What runs on the game's clock each frame outside the stage's walk is a pass an app or a scene owns and updates: `Timers` (`helix.time`) runs callbacks after seconds or every interval, `Tweens` (`helix.tween`) moves values by easings, and `Behaviors` (`helix.behavior`) runs behaviors, each on the node it drives. A behavior is never on a node (decisions 61 and 130: nodes draw; the game's state is the truth and the tree its view): the pass holds the pairs, starts what was added since the last update, in order, updates the enabled ones whose node and every node above it are enabled phase by phase (`Phase`, the class's `@:phase`: every `Input` behavior, then `Simulate`, `Resolve` and `Late`, each phase's in the order added), and stops and drops the ones done. Behaviors don't signal each other: one that decides across entities is a resolver in `Resolve`, gathering what has a say on an entity with `allUnder` (the behaviors of an interface on its node and under it) and applying them in its own order (decision 134). Each `Scene` owns one, which `Scenes.update` runs just before the scene's own `update` under the same gates and clears, stopping each, as the scene exits. The classes are known at compile time: a build macro on every subclass of `Behavior` generates its schema (its `@:prop` fields with types, defaults and ranges) and typed setters, and registers it by name in `BehaviorRegistry`, which a scene file's loader and an inspector read; nothing is found by reflection at run time.

## The scene file

A `.scene` file (`helix.scene.SceneFile`, HeliX's own JSON) sits between the caches, the stage and the pass. `SceneFiles` (the static over `SceneFileCache`, made and bound by the runner beside `Models`) parses a file once and shares it by path; `file.instantiate(stage, behaviors)` makes the tree at once under a group on the stage's root and gives a `SceneInstance`, loading what the file names through the caches that already own it: a `Model` entry's glTF through `Models` (the file's nodes moved under the entry's node when it lands), a prefab through `SceneFiles` (a file naming itself is refused), textures and fonts through `Textures` and `Fonts`, the stage section's environment and background through `Environments`. `SceneKinds` is the live side of `SceneSchema`'s tables, in one module so the two can't drift: the kind's class from its name, each property applied to and read back from the live node. The behaviors a file lists are made from `BehaviorRegistry` and attached to the pass it was given (a `Scene`'s), their references resolved to nodes once every node is made; `ready` comes at the pass's next update, after they started. The instance remembers where each node came from and the values its origin gave it, so `SceneFile.capture(instance)` writes back the file that instantiates to what the tree is now: an untouched instance gives its file byte for byte, a node from a model file or a prefab is written as the reference plus what differs, and a hand edit stays an override. A canonical file says only what differs from the defaults (the stage's, a kind's properties and flags, a behavior's props), so a hand-written default vanishes on capture. Nothing of this is on a node: the instance holds the records and the game's props, the node draws.

## Graphics

`IGraphics` knows no program, layout or pipeline of HeliX's own. The engine describes them as data:

- **Programs:** each framework shader in `src/helix/graphics/shaders/` is compiled by sokol-shdc at build time into a generated Haxe class (`Lit3DProgram` and its siblings) holding the program in both dialects with its bindings (`source()`), its vertex buffers' layout (`buffers()`) and the constants the engine packs vertices and records with. An app's `.hxshader` is the same `ShaderSource`. `IGraphics.createShader` builds either. The shader library's (`helix.shaders`, sources in `src/helix/shaders/`) are packed at build time by `tools/pack_shader.py`, as an app's are, into generated Haxe beside the layouts (`<Name>Packed.text()`, its `.hxshader`; SDL_GPU's dialects in `build/generated/shaders-sdlgpu` for its builds), so a library class gets its shader with no load and a shader nothing uses is left out; `ShaderLibrary` builds each once a GPU, and in development builds a changed one again in place after a hot reload.
- **Shader kinds and their variants:** an app's or the library's shader includes a framework block that decides its kind and supplies the rest. A surface shader (`helix_surface`) packs a skinned variant beside its program and, with a vertex hook or a `discard`, casters static and skinned whose fragment stage is its own over a block that writes nothing (`Shader.skinned`, `Shader.caster`), so a skinned model draws through its material's shader and a shadow follows a hook's movement and a discard's holes. Every material's hit flash and rim are terms of the stage's fragment block that the lit program and every surface shader's `helix_output` apply. Every variant's vertex stage also passes the vertex at rest in the model's own space, its position and normal as the mesh gives them before skinning and the hook (`helix_model_position`, `helix_model_normal`), the one way a surface shader lays a pattern that stays on the surface as a skinned body animates or a hook moves it, and that its casters read alike (`Dissolve`'s triplanar noise). A screen shader (`helix_screen`) draws over a frame. A sprite shader (`helix_sprite`) has the framework's `effect2d` vertex stage and block, whose generated layout is the vertices `Batch2D` packs for a run through an effect, and a `sprite3D` variant over the framework's `sprite3d` vertex stage for a Stage3D's sprites. Texture slots: a surface shader's own from 6 (5 is the joints), a screen shader's from 1, a sprite shader's from 1.
- **Passes on a model:** `ModelPass` (the library's `Outline` and `Silhouette`) draws a model again in a flat color through the framework's `flat3d` programs from the draw's own records, its vertices from the mesh's pass vertices (`Mesh.passVertices`: each position with its normal averaged over every vertex at that position, worked out and uploaded the first time a pass draws the mesh), so an outline's shell pushed out along them stays closed where a low-poly model's normals split at its hard edges. A stage draws its opaque models without a silhouette, its opaque sprites, the silhouettes, the opaque models with one, every outline, then what's see-through.
- **Render targets and the effect chain:** a render target is RGBA8 or RGBA16F (`canRender` says which the GPU draws into), with depth and the screen's multisampling or without either, stored top row first on every backend; a target pass clears it to floats as stored, past 1 in half floats. `PostProcess` draws the scene into one, runs its effects (`ScreenEffect`, each with intermediates at fractions of the frame drawn before its last pass) through two more, and the last over the screen's pass, under the HUD. An effect wanting HDR makes the scene RGBA16F where the GPU can: the stage writes its light untone-mapped as sRGB values running past 1, the scene is cleared to the light the tone mapping shows as its clear color, and a `Tonemap` follows the last effect wanting HDR.
- **Pipelines:** `PipelineDesc` is a program, its buffers' layout, primitive, indexing, blend, depth test and write, culling and winding, depth-only, and the clip flip (what block 0 holds, so an adapter whose render targets are stored upside down can draw them the right way up). `helix.graphics.Pipelines` describes every framework pipeline, makes each once per GPU and keeps it; drawing code asks it at each draw, so a program built again (a hot reload) gets its pipelines made again behind it.
- **Drawing:** one `draw`: buffers by the pipeline's buffer index, an index buffer for indexed pipelines, a range, instances, textures, samplings and uniform blocks by slot.

Resource kinds are the adapter's concern (a cube, a depth array read through a comparison sampler, a data texture read texel by texel), and so is binding each; which kind a program expects is in its `ShaderSource`.

## What each audience needs

| To... | Needs |
| --- | --- |
| Build and run a game in a browser | Haxe. Node and Terser only to minify a release build. |
| Build and run a game natively (Linux) | Haxe, hxcpp, a C/C++ compiler, and the native adapters' system libraries: X11/Xrandr/Xi/Xcursor and GL (window, graphics), ALSA (audio output), the libsndfile runtime with Vorbis, Opus and mpg123 (compressed audio). |
| Write shaders (an app's `.hxshader`, or the framework's) | sokol-shdc, and Python with PyYAML for the packer and generator. |
| Develop HeliX itself | The above, plus hotreload-hx (the dev loop), Node with Playwright and pngjs (browser checks); FFmpeg only to remake Asteroids' sounds or the test fixtures, which are committed. |

Today a fresh checkout also needs sokol-shdc and Python to build at all, because the framework's generated shader code isn't committed. Since that code is now pure Haxe (sources and vertex layouts as data), committing it, or shipping it in a release, would take both off a game developer's list; shader authors and HeliX's own development keep them. Python is the tools' language (the build and dev driver, the shader packer and generator, the checks); moving them to Haxe's interpreter is possible, the YAML reflection reader being the one piece Haxe lacks. Wasm (physics, later) would be built by maintainers with Emscripten and shipped prebuilt; natively the same C/C++ links through hxcpp.
