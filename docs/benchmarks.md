# Benchmarks: web sizes

Generated by `tools/measure_sizes.py --write` from `benchmarks.json`, the baseline CI holds to (`--check`, in `helix.py test`: a rung more than 1% and 1 KB larger, gzipped, fails). Each library has a ladder of programs on it and what it sits on, each constructing only what it uses. Every rung is a release browser build (`-dce full`, the analyzer), its JavaScript unminified, as Haxe alone writes it; sizes in KB.

Measured from bf3efe1 2026-11-02 with Haxe 4.3.7.

## helix-ray

Programs written in raylib on helix-ray (`ray/tests/sizes/`), each adding one feature to the one before, from a window cleared each frame: what a feature costs through raylib's API is its row's increment, gzip; brotli in brackets. Against the services' ladder this is what the familiar API costs (DECISIONS 15): helix-ray's window brings its time, the screen (with the saves it keeps its state in) and the keyboard, so its first rung holds them; the rest (the assets its files load through, the image decoder, the dropped files) comes with the functions that need it (DECISIONS 30). Each rung's `@:adds` names what it adds. Its 3D starts with a cube made in memory (GenMeshCube, LoadModelFromMesh), drawn unlit with a camera: the 3D drawing alone, so the glTF rung after it is the reader's own cost. helix-ray's bytes are counted by source file: raylib's modules (R*) and its internals, its facade and structs as ray. The last two rungs are its high-water marks. The game is what a real game uses, one file format of each kind (a skinned, blended glTF model, PNG textures, a TTF font, WAV sounds and Ogg music, every input, a save, a shader and a render texture). The kitchen sink calls every function of `Raylib`, `Raymath` and `Rlgl` that compiles, written as the program builds (its `Everything.hx`), and every reader by a constant name of each extension, so nothing of helix-ray is left out: it is the comparison point for whole-library sizes, such as an Emscripten build of raylib exporting everything.
