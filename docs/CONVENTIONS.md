# HeliX conventions

Rules for HeliX's public API, its examples, and the agents working on them. Names are predictable from what they do, so code and agents can find an API before reading it.

## No backward compatibility

HeliX has no users to protect. When an API changes, every caller changes with it in the same commit: examples, tests and tools. Nothing keeps an old name, an old signature or an old behavior alive beside the new one: no aliases, deprecated wrappers, compatibility flags or shims.

## Names

HeliX is Haxe through and through, and its API uses what Haxe gives: properties for values, classes for kinds, static classes for the program's one set of services. The earlier C frameworks' rules (a method for everything, so a binding could be made of it; a type field instead of a class) were theirs, not Haxe's, and were dropped (DECISIONS 130).

| Kind | Form | Example |
| --- | --- | --- |
| A value | a property, read and assigned | `Window.title = "Asteroids"`, `light.intensity = 2`, `node.visible = false` |
| Several values set at once | `setX(...)` | `node.setPosition(x, y, z)`, `camera.setView(eye..., target...)` |
| A state now (a bool) | an adjective property | `node.visible`, `clock.paused`, `pad.connected` |
| A state asked with an argument | `isX(...)` | `Input.isDown(Key.A)`, `Input.isFramePressed(Key.Space)` |
| Whether an action is possible here, so whether to offer it | `canX()` | `Window.canMove()`, `Host.canQuit()` |
| Ask for what the platform may refuse or grant later | `requestX(...)` | `Window.requestFullscreen(true)`, `Window.requestSize(800, 600)` |
| An action | a verb | `Host.quit()`, `stage.add(node)`, `Models3D.load(path, done)` |
| A count or a limit | a property naming what it counts; the limit first | `Input.padCount`, `Graphics.msaaSamples`, `Graphics.maxMsaaSamples`, `ticker.maxSteps` |
| Fill what it's given | a verb, not a property | `camera.computeRay(x, y, ray)`, `node.computeWorld(out)` |
| A command for what follows in a pass | `applyX(...)` (sokol's word) | `Graphics.applyViewport(...)`, `Graphics.applyScissor(...)` |

- **A value is a property.** One that must act when assigned (a node's `x` dirties its matrix, a material's `baseColor` marks a GPU update) has a `set_` accessor; one read back from somewhere else has a `get_`; one nothing may assign is `(default, null)`. A record made whole and never changed after (`Touch`, a parsed header, a progress report) shows `final` fields. Nothing public is a bare `var` that something else keeps in step by hand.
- **A property clamps; a method may refuse.** Assigning can't answer, so a property takes what it's given, held to its range (an intensity under 0 is 0, a cone past its outer is the outer), and its doc comment says the range. Whatever can be refused or decided later is a method returning `Bool`: `requestSize`, `add`, `load`'s result.
- **`request` returns whether it asked, never whether it was granted.** The answer is read back later from a property: `requestFullscreen` returns whether the request was made; `fullscreen` says, on a later frame, whether it was granted. `can` says whether to offer the request at all.
- **No chaining.** A method that changes something returns `Void`, or `Bool` when it can refuse; none returns its object. Building something takes one statement a line.
- **A completion takes a lambda per outcome, success first:** `Models3D.load(path, file -> place(file))`, with the failure's lambda optional (`Models3D.load(path, file -> place(file), message -> caption = message)`): one left out is logged with the path, so nothing fails silently, and a cancelled request calls nothing, as its caller cancelled it. No result enum to switch on. A lambda made before a reload runs the code it came from (hotreload-hx), so a completion's lambda calls a method by name, `file -> place(file)`, never passes the method itself (`place` binds the old code when it's passed). In the browser the method it reaches is then the new one, and only the lambda's line is old for the frames a load takes. Natively an old lambda runs its old module through and through, and the `this` it captured is a copy the new code has left behind, unless what it calls is a `@:hot` static function, which every old closure reaches at its newest (hotreload-hx ef1d678); the browser loop is where reloads happen, and a game that must survive a native reload mid-load makes its completion `file -> Game.onLoaded(file)` with `onLoaded` a `@:hot` static. The build warns where a method is passed as a value. A callback registered once for the program's life (a frame, a resize, an input) is registered by the main class or again from `@:afterHotReload`, never kept from before.
- **Kinds are classes.** A `Node` is a name, the flags (`enabled`, `visible`, `pickable`), a parent and children, and `find`; a `Node3D` and a `Node2D` add their transforms, each taking children of its own kind only. What a stage holds is a `Node3D` and the framework's kinds on it: `Model3D`, `DirectionalLight3D`, `PointLight3D`, `SpotLight3D`, `Camera3D`, `Sprite3D`, `Text3D`, `Particles3D`, and on `Node2D`: `Sprite2D`, `Shape2D`, `Text2D`, `Particles2D`. A class holds only its kind's data. A game never subclasses a node, and nothing but drawing is a node: a behavior is run by a pass (the program's `Behaviors`, or a `BehaviorPass` of the game's own), holding the node it drives (DECISIONS 61 and 130).
- **A behavior is a class extending `Behavior`** (`helix.behavior`), run by a pass (`BehaviorPass`; the program's is `Behaviors`, run by the runner after `update`), never by a node: `node` (the `Node3D` it drives, set by the pass before `start`), `enabled`, `done` (set true to end), and `start()`, `update(dt)`, `stop()` to override. Its props, what a scene file or an inspector sets, are `@:prop public var` fields with an initializer (`@:prop public var radius = 4.;`), of `Int`, `Float`, `Bool`, `String`, `Array<Float>`, a color (`@:prop("color")` on an `Int`) or `Node3D` (a reference); `@:range(min, max)` on a field gives an inspector its range; `@:behavior("Name")` on the class registers it under another name than the class's. The build macro generates the class's `schema()`, its typed setters and its registration in `BehaviorRegistry`, so a file names a behavior and nothing is found by reflection; a class only a file names must be in the build (`--macro include("pack")`). The program's pass, `Behaviors`, runs after the app's `update` by the game's clock, so a behavior on a node held `paused` waits; a `BehaviorPass` of the game's own is updated by whoever made it, as a `Tweens` is. A phase says when in a frame a behavior runs: `@:phase(Late)` on the class, one of `Phase`'s `Input` (reading devices, deciding intent), `Simulate` (moving the world; the default), `Resolve` (settling what Simulate produced: checkpoints, hits, triggers) and `Late` (following the settled world: cameras, HUD anchors, effects), run in that order. Behaviors don't signal each other: a capability is an interface a behavior implements (`IDamageModifier`), and a system that decides across entities is a resolver behavior, found with `pass.find`, which the others report to, gathering the participants with `pass.allUnder(node, IDamageModifier)` (gear on the entity's child nodes) and applying them in a fixed order of its own.
- **A game asks for actions, not keys.** Its controls are an `Actions` map (`helix.input`) over the input, `actions.bind("jump", Keyboard(Space))` and `actions.bind("jump", Pad(South))` in code, read as `actions.isPressed("jump")` and `actions.axis("steer")`, so a player can rebind them (`capture`) and keep them (`save`, `load`), and a pad or a touch region works where a key does. Reading a key with `Input.isDown(Key.A)` is for what isn't a player's control (a debug key, a text field). Action names are strings; a game wanting them typed writes an enum abstract over `String` and passes its values.
- **The program's services are static classes:** `Host`, `Window`, `Input`, `Graphics`, `Stage` (what's drawn, docs/DISPLAY_MODEL.md), `Behaviors`, `Audio`, `Assets`, `Storage`, `Saves`, `Fetch`, `Textures2D`, `Fonts2D`, `Models3D`, `Environments3D`, `Time` (the program's clock and frame timings), `Screen` (the presentation), `Screenshots`, `TestHarness`, each one instance for the one program (a singleton), forwarding to the instance the runner gave it (`Window.instance`, an adapter; `Models3D.instance`, a `ModelCache3D`: the class a static stands over takes a `Cache` or `Service` suffix, `TextureCache2D`, `FetchService`); the forwarders are generated from the service's interface by a build macro, so nothing is written twice, and the interface stays the adapters' and the tests' side. A game calls a service through its static (`Input.isDown(Key.A)`, `Screen.visibleWidth`); the instance a static forwards to is the engine's alone (`@:allow(helix)`), so a game can't reach around it, and a test gives the code it tests a fake by binding the static (`@:privateAccess Input.bind(state)`), as an autopilot binds its script's input while it plays. An API a game calls takes a service as an optional last parameter, the program's when not given (`Texture2D.renderTarget(256, 256)`, `new PostProcess()`, `new Pointer()`), and what keeps one reads it when used rather than when made, so it works made before the program runs and follows an autopilot's input; the engine's own wiring (a cache the runner builds, a GPU buffer) keeps its required one, which is how tests give theirs. A thing a game makes for itself (a `Clock`, a `Ticker`, a `Renderer3D`, a `Tweens`) is an ordinary class with instances.
- **An optional part is installed by its first use** (GOALS.md, 1): a service a program may never use (environments now; screenshots, audio and the others as they move) is reached only through its static class, which installs it the first time (`helix.macro.Facade.build`'s install, `Host.installPart`), and the Runner walks its parts' hooks (`helix.host.Part`: poll, frame end, busy, shutdown) without naming one, so a program that never uses a part carries none of its code. `tools/measure_sizes.py`'s ladder shows where each part's cost lands.
- **A static survives a hot reload only if it says `@:hot`, on both targets.** In the project's own code (its class paths, `src/` and `examples/`, less the main class; the standard library and haxelibs keep theirs), a plain static starts over from its first value at every reload (hotreload-hx b9aa033), so an edited initializer takes effect; a static holding state that must outlive the swap (a service's instance, an id counter, a cache the reload's hook rebuilds from) carries `@:hot`, with a comment saying why. A closure or a bound method kept in a static runs the code it came from (DECISIONS 123).
- **A sound is played through its bus**, a `Bus` object held as any reference: `Audio.music.play(theme, true)`, `ambience.play(rain, true)` for `final ambience = Audio.addBus("ambience", Audio.effects)` (a `@:hot static final` where it must outlive a native reload), `Audio.play(sound)` for the effects bus. A bus's name is only for saving its volume (`Audio.saveBuses`); volumes are 0 to 1 and fades take seconds, linear in decibels.
- **One concept, one name across types:** a sprite's part of its texture is its region everywhere (`regionX`, `regionWidth`), not a region here and a source there.
- **Adapter classes are `<Api><Contract>Adapter`**, words the API's name ends with and the contract's starts with written once (`WebAudioAdapter`, not `WebAudioAudioAdapter`); ARCHITECTURE.md has the directories, and `tools/check_adapters.py` checks both.
- **A directory is a directory,** as Haxe's standard library names it (`FileSystem.readDirectory`, `Path.directory`) and as programming APIs generally do: in names, doc comments and docs, never "folder" (the desktop's word) or "dir" (an abbreviation): `serveDirectory`, `assetDirectory`. Only a third party's own name keeps its word.
- **2D and 3D are named apart, always:** a type of one kind ends in its kind, whether or not the other kind has a counterpart yet (`Camera2D` and `Camera3D`, and as much `Model3D`, `Mesh3D`, `Material3D`, `Light3D`, `SpriteSheet2D`), so no one guesses which kind a name means, and a counterpart arriving later renames nothing. That holds for every public type of `helix.render2d` and `helix.render3d`, its services and their caches too (`Textures2D` over `TextureCache2D`, `Models3D` over `ModelCache3D`); for a module named for a kind, whose subtypes are its kind's (`Node3D.Attachment3D`, `AnimationClip3D.Track3D`, `Layout2D.Sizing2D`); and for a family named by a file of one kind (what a `.scene3d` holds: `SceneFile3D`, `SceneNode3D`, `SceneMaterial3D`, `NodeRecord3D`). Only what holds both kinds or neither keeps a plain name: a file format (`Gltf`, `Hdr`, `Ktx`, `TrueType`), `Mat4`, `Tonemap`, the display holding both (`Stage`, `View`), and what both kinds' scene files will share (`SceneBehavior`, `SceneValue`, `KindSchema`). The kind ends the name (`LayoutDirection2D`, not `Layout2DDirection`). A type both kinds use is neutral and lives outside them (`helix.graphics.AlphaMode`, a sprite's and a particle's way with alpha), and 2D code names no 3D type. `tools/check_names.py` checks it, its lists of the plain ones each giving the reason.
- **Capitals:** `2D` and `3D` keep a capital D. Acronyms are written as words, as in Haxe's standard library (`Json`, `Xml`, `Http`): `id`, `Url`, `IndexedDb`. Product names keep their own spelling (`WebGL2`, `Sokol`).

## Units

One unit per kind of value across the API, so nothing has to be converted at a call:

- **Angles are radians.** A positive angle turns from +x toward +y: clockwise on screen in 2D, where y grows downward. 3D is right-handed with +y up.
- **Time is seconds**, as a `Float`. A value in another unit says so in its name (`WorkQueue.budgetMs`) or, where the name can't, in its doc comment (`Time.frameCpu` and `frameInterval` are milliseconds).
- **Colors are `0xAARRGGBB`** integers, alpha in the top byte, as Haxe's libraries write them and as an editor's color picker reads a literal; `helix.graphics.Color` gets and sets their channels. Text writes a color the CSS way, `#RRGGBB` or `#RRGGBBAA` (a scene file, a color picker's field), converted by `Color.fromRgba` and `toRgba`.
- **A simulation that must play alike on every target** (an autopilot's replay, lockstep, physics) takes its trigonometry from `helix.math.Trig`, never `Math`'s `sin`, `cos`, `tan`, `atan2`, `asin`, `acos`, `exp` or `log`, which differ in the last bit between the browser and native. Arithmetic, `sqrt`, `floor` and `pow` agree. Drawing may use `Math`.
- **Positions and sizes name their space** in the doc comment: framebuffer pixels (`IWindow`'s framebuffer size, the pointer), logical pixels (the window), or world units (a camera's).

## Layout and documentation

Code is written to be read, by people and agents, not packed.

- **Formatted by the tool, not by hand.** Haxe source is laid out by haxe-formatter (`formatter` on lib.haxe.org) with the repository's `hxformat.json`: one statement per line, indented blocks. Formatting is checked with the other checks, so dense one-line classes and functions don't come back.
- **Every public type and member has a doc comment** (`/** ... */`) saying what it is or does, in the units it uses, with its ranges and every refusal ("False for ..."). Private code gets a comment where the reason isn't plain from the code.
- **Generated API documentation.** The doc comments are the API reference: dox (`dox` on lib.haxe.org) generates it from them, so what a developer or an agent reads is what the code says.

```console
python3 tools/format.py         # lay out the Haxe source; --check only checks
python3 tools/check_docs.py     # list public API without a doc comment
python3 tools/check_types.py    # every entry point, both targets, in seconds
python3 tools/gen_apidoc.py     # the API reference: docs/api (committed; --check in the tests) and build/api/index.html
```

- **Tools are named for what they are:** a runnable tool is verb_noun, words apart by underscores (`check_types.py`, `gen_manifest.py`, `bake_fonts.py`, `gen_code.py`); a `check_` tool only reports, a `gen_` tool makes files (committed ones, remade with `--regenerate`), the rest do what they say. A converter is `<from>2<to>`, naming both ends (`fbx2glb.py`, `gltf2scene.py`). A module only imported by other tools is named for what it holds, a plain noun that can't read as a verb (`shader_metadata.py`, `variants.py`). Front doors keep their noun (`helix.py`, `tools/example.py`, `tools/services.py`, `tools/pages.py`). What a game runs is Haxe, on the library's class path in `helix.tools` (`src/helix/tools/`), named as any class: the build steps its hxml lists as macros (`Build`, `Watchers`, `WebServer`, their methods named for what they do, `Build.generateWebPage`), what they share in packages behind them (`helix.tools.setup`, `helix.tools.shader`, `helix.tools.shared`), and `haxelib run helix`'s commands through `Run.hx`; run in the compiler or its interpreter, so a game needs no Python, and never compiled into a game. The same for the Node scripts beside them (`check_cache.cjs`).

- **Generated code a build compiles against is committed, in `generated/`,** and its generator writes there, never into `build/` (which holds only scratch: `tools/gen_code.py`, decision 138); `--check` in the tests fails when it isn't what the sources give. So a build on `-lib helix` needs no generator, and a commit carries what it compiled.

The formatter and dox are pinned in `dependencies.json` and installed into the repository's own haxelib (`build/haxelib`), as hxcpp is.

## Build

A build is named `<platform>-<config>-<backend>[-<option>...][-<sanitizer>]`, each part chosen from a fixed list, so a name says what was built and where it is (`tools/variants.py` holds the lists and the directories; DECISIONS 137).

- **platform:** what the program links against, this machine's for a native build: `linux-x64`, `linux-arm64`, `macos-arm64`, `macos-x64`, `windows-x64-msvc` (hxcpp's default on Windows; `windows-x64-mingw` would be MinGW's, not supported yet), and `js` for the browser.
- **config:** `debug` or `release`. `release` is what ships: full dead-code elimination, the analyzer's optimizations, Terser in the browser. `debug` finds faults: Haxe's `-debug` (a source map in the browser; natively hxcpp's debug runtime with stack lines and null checks), the standard dead-code elimination, no optimizer, and the adapters' C unoptimized with its assertions and sokol_gfx's validation on.
- **backend:** always named, never implied by the platform: the exact API the build draws with, `webgl2`, `sokol-gl`, `sdl3-gl`, `sdl3-gpu`. sokol is built for GL on every system today, so its Direct3D 11 and Metal builds, when they come, are `sokol-d3d11` and `sokol-metal`; WebGPU's is `webgpu`. `sdl3-gpu` is SDL_GPU, whose driver (Vulkan, Direct3D 12, Metal) SDL picks as the program starts. A profile is named for its backend (`Sdl3GpuProfile`), and a build names its backend to `helix.App` with `-D helix-backend=sdl3-gpu`. A `headless` backend (no window or GPU, for tests) is to come; none exists yet.
- **options**, then a **sanitizer**, in that order: a name only adds, never `-noX`. The one option is `dev`, the browser's page with hot reload built in, which only the dev loop makes (`js-debug-webgl2-dev`); there are no sanitizer builds yet.

A build's results go to `out/<platform>/<config>-<backend>[-<option>...]/`: natively `bin/<example>/` holding the program, named for its example, and what it loads beside it; in the browser `site/<example>/`; and beside the examples' directories the `assets/` they share, which each loads as `../assets`, so `bin/` or `site/` is what ships. Everything else the build makes is scratch in `build/<name>/` (the HXML, hxcpp's generated C++ and objects). The tools write all of `out/`, so deleting it is a clean; nothing reads results from `build/`. The tools take `<config>-<backend>` with the platform this machine's, or the whole name:

```console
python3 tools/example.py asteroids build release-sdl3-gpu      # out/linux-x64/release-sdl3-gpu/bin/asteroids/asteroids
python3 tools/example.py asteroids build                        # release-webgl2: out/js/release-webgl2/site/asteroids/
python3 tools/example.py asteroids autopilot debug-sokol-gl --browser ...   # against js-debug-webgl2
python3 tools/example.py asteroids dev                          # js-debug-webgl2-dev
```

## Examples

- An example shows a feature through the framework's API. Work that a game would otherwise repeat (hit tests, timers, layout) belongs in the framework; an example that has to do it by hand says so in its comment.
- Examples are developed in the browser hot-reload loop. Native builds, unit tests and cross-target checks run at checkpoints (the end of a feature or milestone), not after each change.
- Native checks that drive a window run on a private display (`tools/private_display.py`), never on the user's desktop: a new window takes the keyboard focus, so the user's typing would land in it.
