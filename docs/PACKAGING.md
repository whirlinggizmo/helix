# Tools, autopilot and the haxelib

The useful package boundary is the Haxe framework API and utilities, with separately selected platform adapters. A game depends on the services' static classes the `Runner` binds (`Window`, `Input`, `Graphics` and the others) and the shared policy above the platform contracts (`IHost`, `IGraphics`, `IInputSource`, `IAudio`, `IAudioDecoder`, `IHttp`, `IStore`, `IImageDecoder`, `ITestHarness`; [ARCHITECTURE.md](ARCHITECTURE.md)); browser externs and native bindings belong underneath them, in adapters. Native compiles Haxe through hxcpp, which builds the adapters' C (sokol, or SDL3 with SDL_GPU) with each program from the build XML on each adapter's extern bridge. A haxelib can include native sources/tools as well as Haxe; packaging does not remove that glue. See the [official package guide](https://lib.haxe.org/documentation/creating-a-haxelib-package/).

## What exists and was tested

`src/helix/` contains contracts, input accumulation, path validation, asset cache policy, cooperative callback queues, audio resource/playback lifetimes, PCM/WAV utilities and JSON autopilot. It imports no Asteroids, adapters or generated shader types. Examples, Asteroids and Blocks among them, are applications on top of it: `examples/asteroids/src/` holds game, menu, drawing (through `Batch2D`) and sound policy. Adapters implement the contracts; the shared launchers in `examples/shared/launch/` run the app through an explicitly named profile from `src/helix/profiles/`, which picks the adapters. Framework/game contain zero target conditionals. Canonical WAV validation/decoding is Haxe (the shared `AudioDecoding`); Ogg/Vorbis, Opus and MP3 decoding is `IAudioDecoder`'s: browser Web Audio or native libsndfile through a small C bridge. Sokol C supplies graphics/events/PCM delivery, while browser audio/fetch/storage stay in browser APIs. Native package consumption must supply libsndfile/codec dependencies and preserve the recorded LGPL SDK/library notices; the decoder is not shipped in browser Wasm.

Autopilot scripts replay alike on every target when they wait on state, never on time, for anything that isn't the simulation's (`wait` on a probe with a limit in `seconds`; `click` a UI widget by name, waiting until it's usable, as web suites' actions do), counting ticks only for what the simulation itself does; and when the game starts each replayed phase from a known state (play fresh from the seed, however late it starts; a title screen's motion is dressing). Then a menu, a slow load or a frame's timing can't change the game (`helix.debug.Autopilot`).

`tests/consumer/PackageSmoke.hx` is a separate consumer compiled and executed with only the framework and test classpaths under the Haxe interpreter and JS/Node. It checks reusable input and autopilot behavior and type-checks the service contracts. The examples run against both real adapters. This proves a source boundary; the haxelib below proves the installed one.

The framework's shaders (`src/helix/graphics/shaders/`) are pure-Haxe program classes (`Sprite2DProgram`, `Lit3DProgram` and their siblings) holding each program's source and buffers as data; adapters name none of them. They are generated into `generated/`, committed and shipped with the library (decision 138), so sokol-shdc and Python are off a game developer's list (ARCHITECTURE.md). Avoid expanding the API into a new general GPU framework merely to make packaging look complete.

## The haxelib

HeliX is a haxelib since milestone 14: `haxelib.json` (`classPath` `src/`, no dependencies, so installing it pulls nothing a browser-only game doesn't need), and `extraParams.hxml`, whose one line, `--macro helix.macro.Haxelib.configure()`, adds what every build on `-lib helix` needs beyond the class path: the generated code's directories (`generated/shaders`, `generated/fonts`; `generated/shaders-sdlgpu` under `-D helix_sdl3_gpu`), resolved from the library's own location, since a relative `-cp` in extraParams.hxml resolves against the game's directory, and natively hxcpp's architecture define for the machine building. The adapters' build XML anchors on `${haxelib:helix}`, the codec links libsndfile by its soname on Linux unless a build names the library. A game installs Haxe, hxcpp for native builds, hotreload-hx for the dev loop, and nothing more; `templates/index.html` is its page and its asset directory sits beside the page or the program ([BUILDING.md](../BUILDING.md), "A game on `-lib helix`"). A game builds with hxml files whose build steps are macros in `helix.tools` (`src/helix/tools/`, run by the compiler, so a game needs no Python): `Build` packs the game's `shaders/*.glsl` into `assets/shaders/` as the examples' are, generates the page beside a browser build, and makes a distribution (`cleanOutput`, `generateWebPage`, `copyAssets`, `copyProgram`, `zipOutput`, with `index.html` at the zip's root for itch.io); `Watchers.watchShaders` repacks shaders on save; `WebServer.serveDirectory` serves a build to try. `haxelib run helix` (`haxelib.json` names `Run.hx` as its `main`, which haxelib runs in the library's directory with the caller's directory appended, by Haxe's interpreter) is for what comes before an hxml: `init` writes a starter game, with its hxml files; `setup` fetches the shader tools ahead (`tests/tools/helix_tools_test.py`). Dogfooded by a hello game outside the repository under `haxelib dev`, built and run in the browser and natively from `-lib helix` alone, its site served under a subpath in headless Chrome; the starter built and run both ways. Not built: the package archive and its publication.

## Build front door

Use HXML for Haxe compiler settings and Python for external-tool orchestration. `tools/example.py` writes each example's HXML (classpaths, target, DCE and analyzer settings, by the build's name: `<platform>-<config>-<backend>`, [CONVENTIONS.md](CONVENTIONS.md#build)) and coordinates sokol-shdc, structured shader metadata, font baking, an example's own asset recipe, hxcpp (which compiles the native adapters' C with each app) and Terser. It passes argument lists, with no shell-script dependency. The [Haxe HXML documentation](https://haxe.org/manual/compiler-usage-hxml.html) describes the compiler's own configuration format.

From the repository root:

```console
python3 tools/example.py asteroids dev                          # hot reload in the browser (js-debug-webgl2-dev)
python3 tools/example.py asteroids build release-sokol-gl       # out/<platform>/release-sokol-gl/bin/asteroids/
python3 tools/example.py asteroids autopilot release-sokol-gl --browser /path/to/chromium
python3 helix.py test --native
python3 helix.py services --browser /path/to/chromium --native release-sokol-gl
```

`helix.py test` runs the adapter check (`tools/check_adapters.py`), checks the test fixtures are there (`tools/gen_fixtures.py`, which makes them with FFmpeg only when one is missing), then runs the tool tests (`tests/shaders`, `tests/tools`), the package smoke test, every unit test, the deterministic trig check (interpreter and JS, and hxcpp with `--native`) and, with `--native`, the C service tests. `services` runs the asset, storage, fetch and audio services against local HTTP fixtures. Native execution/linking is Linux only; Python/Haxe tooling uses portable process/path APIs.

A game's builds are its hxml files, their steps `helix.tools`' macros; `haxelib run helix` (`Run.hx`, the library's `main`) runs `init` and `setup` (`helix.tools.setup`), above and in BUILDING.md. They're on the library's class path, run in the compiler or its interpreter, and never compiled into a game: nothing there is reached from a game's code.

## Autopilot

Autopilot loads a packaged JSON file through `IAssets`, supplies normal named input through `IInput` (its presses activate `IInput.activated` as a user's would, so a game gated on it is pressed before the script waits; real browser audio stays locked, as synthetic events carry no activation, and `AudioResources` waits as it does for any early start), and observes only an explicit `String -> Dynamic` probe callback provided by the app. It drives the same `Controls`, menu and simulation as interactive play. It does not edit game state, inspect private fields or scrape source files. Ordinary `haxe.Json` parsing and `Reflect` field validation are used for the JSON schema; shader reflection remains an unrelated offline build step.

The schema is version 1, with a deterministic seed and up to 128 commands:

```json
{
  "version": 1,
  "seed": 12345,
  "commands": [
    {"op": "press", "key": "ENTER"},
    {"op": "wait", "probe": "state", "equals": "playing", "timeout": 120},
    {"op": "hold", "keys": ["UP", "SPACE"], "ticks": 120},
    {"op": "assert", "probe": "shots", "atLeast": 6}
  ]
}
```

`press` lasts one simulation tick. `hold` specifies a tick count. `wait` has exactly one `equals` or numeric `atLeast` condition and a timeout; optional `keys` remain held while waiting. `assert` checks immediately without advancing time. Durations/timeouts are limited to 36000 ticks per command; unknown fields, commands, key names, duplicates and invalid bounds fail. Each game exposes its own probes (Asteroids: state, score, best, lives, wave, shots, deaths and hits) while reusing the command runner.

A point (a `sample`'s, a `drag`'s `from` and `to`) is either `[x, y]` in the design's units (`Screen`'s) or a point on a UI widget, so a script keeps working when padding, gaps, separators or a widget's size move the layout: `{"target": "background", "at": [0.5, 0.5]}` at fractions of the laid-out rectangle of the widget named `target` (0, 0 its top left, 1, 1 its bottom right; past them, just outside it), or `{"target": "background", "part": "hue", "at": [0.33, 0.5]}` of one of its parts. The parts (`Ui.computePoint`): a `Slider`'s `track` (its value from min at its left edge to max at its right); a `ColorPicker`'s `square` (saturation across, brightness down), `hue` and `alpha` (each bar between the centers of its round ends, so `at`'s x is the value) and `swatch`; the `track` and `thumb` of a `ScrollArea`'s or a `ListView`'s scrollbar while it shows; a `ListView`'s `row:<index>`; and, while a `Dropdown`'s list is open, its `list`, `row:<index>`, `track` and `thumb`. A widget's point is found through the app's `locate` callback (`Ui.computePoint`, in framebuffer pixels through the UI's camera, where the widget was last drawn) whenever it's used: a sample's as it asks for its frame, a drag's `from` as it presses and its `to` again every tick, so a moving layout is followed. One not found (no such widget shown, or no such part now) is waited for, as a `click` waits, ticking, within the command's `seconds` (5 when it gives none), and then fails the script naming the widget and part. A `click` with `at` (and `part`) clicks the pointer there, pressing on one tick and letting go on the next, instead of using the widget by name: `{"op": "click", "target": "quality", "part": "row:3", "at": [0.5, 0.5], "seconds": 5}`. A sample's snapshot keeps its points as found, in the design's units. What isn't a widget (a model in a 3D view) is sampled at design points.

`python3 tools/example.py <name> autopilot [<config>-<backend>] --browser /path/to/chromium` builds the native build (`release-sokol-gl` when not told) and the browser's in the same config, and replays every script in `examples/<name>/autopilot/` in a headless browser and natively on a private display, with sound off and fast mode on. Both must publish the same final game, and the same colors at the points a script samples (`{"op": "sample", ...}`: within 3 per channel, or the sample's own tolerance); a script drags the pointer (`drag`, from and to in the design's units or on widgets) and types text (`type`) as a player would; reports go to `build/results/<name>/`. Fast mode advances up to 120 fixed ticks per frame where the example supports it; its wall time is a correctness convenience, not a performance result.

Manual browser use: `?autopilot=autopilot/asteroids/playthrough.json&fast=1&audio=0`. Native: `HELIX_AUTOPILOT=autopilot/asteroids/playthrough.json`, `HELIX_FAST=1`, `HELIX_AUDIO=0`. The scripts are under `autopilot/<example>/` in the build's shared assets directory (below).

A build's examples share one assets directory beside them, `out/<platform>/<config>-<backend>/bin/assets` (`site/assets` in the browser), which every example loads as `../assets` (the shared launchers pass it to the profile: the browser's asset base, a native profile's asset directory relative to the program). It holds `examples/assets` once, and each example's own files: its autopilot scripts as `autopilot/<example>/`, its own `assets/` directory (a `gen_*.py` there makes what is missing first; Asteroids' sounds are committed) and its packed shaders. An example's own file may not claim a path that a shared file or another example has; the build stops and names both. So a build's examples carry their 8 MB of shared files once instead of each a copy, and an example's directory runs beside its build's `assets` rather than alone. The browser's directory carries asset manifests (`tools/gen_manifest.py`, written on every build and when the dev loop repacks a shader), which the page's asset cache follows so a returning visitor re-fetches exactly what changed (DECISIONS 111); `python3 tools/check_cache.py --browser <chromium>` checks it across visits. The dev server serves its own build's (`js-debug-webgl2-dev`) at `/assets` (hotreload-hx's `--mount`). A game of its own passes `"assets/"` (browser) or `"assets"` (native) and keeps its files beside itself.

## Recommendation

Proceed toward a Haxe library with platform adapters. Keep application code outside it and choose adapters in build configuration. Keep the Python front door now, with the optional Haxe launcher for convenience. Neither tool contributes runtime bytes to the delivered game.

The haxelib exists and an independent application builds against it (above); shader generation is the library's (`generated/`), and the native build integration hxcpp's, from the adapters' build XML. Before publishing a package: the version policy (`haxelib.json` follows the milestones today), the lifecycle and handle contracts stabilized, and how the Sokol and SDL versions the adapters vendor are supplied to an installed copy, which `haxelib git` and `haxelib dev` carry whole.
