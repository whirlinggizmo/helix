# Roadmap

What comes next, milestone by milestone. What's done, and when: [HISTORY.md](HISTORY.md). Why each piece is the way it is: [DECISIONS.md](DECISIONS.md).

Each milestone reimplements a part of the earlier frameworks (wgrender-c, libwgf, libwgt) feature by feature, as examples that run in the browser and natively. Mid-milestone, work is checked in the browser with hot reload and the interpreter's unit tests; a milestone ends with the full checks on both targets.

## Next

- **Milestone 14: HeliX as a haxelib, and the examples written as a game would write them.** A game anywhere on disk takes the framework with `-lib helix`, as it would Heaps or OpenFL, and HeliX's own examples are built exactly that way, so the library path is what's developed every day. Begun 2026-10-20 (174049e: `haxelib.json`, the adapters' build XML anchored on `${haxelib:helix}`), dogfooded by a hello game outside the repository (`~/projects/local/haxe/hellohelix`, `haxelib dev`): it built and ran in the browser and natively and hot reloaded under hotreload-hx's own dev server with no HeliX tooling. What it still had to do that a game shouldn't, which is the work: the generated code (the framework programs, the packed shader library with SDL_GPU's dialects, the built-in font) committed inside the lib under a listed class path, kept current by CI, so a build needs Haxe and hxcpp only (today two absolute `-cp` to the checkout's build/generated); one entry point, `helix.App`, Heaps-style (a game class extends it, overriding `init`/`frame`/`cleanup`; `Main` does `new Game()`; its constructor picks the profile by `-D helix-backend=` and runs, so no Main per backend; `PageState`, `DevKeys` and `ScreenShape` become its options, on in debug builds) with the Runner's calls into the game as `@:hot` static springboards holding the app in a `@:hot static`, which is what a native reload needs (hotreload-hx never reloads the main class natively, and a call from code compiled before the reload reaches new code only through a `@:hot` static function; on JS old classes forward, so it costs nothing there); `Batch2D` sizing an unsized `Camera2D` to the framebuffer (a fresh camera is a 1 x 1 viewport and draws nothing); `extraParams.hxml` carrying `HXCPP_M64`/`ARM64` per host and hxcpp as a declared dependency (the repo's pin in build/haxelib stays the repo's); the codec's defaults for Windows and macOS and the DLL beside the program, and the SDL3 backends' library found from the lib; an `index.html` template and the asset directory placed beside the page or the program by the build; a game's own `.glsl` packed by its build and on save (`helix.tool.Build.packShaders`, `Watchers.watchShaders`). Then every example becomes a directory a user copies as a starting point: its own hxml files (`-lib helix`, or `-cp ../../src` from an include when developing HeliX itself, so engine edits reload into it as now), `Main`, `src/`, `assets/`, autopilot scripts and `config.json`, the shared launchers and `examples/shared/src` gone into the engine, `tools/example.py` a loop over those directories running the same commands a game runs plus what forty of them need (build all, the autopilots, the site); which shared assets a copied example carries is decided then. **Done when:** the hello game and every example build for the web and natively from `-lib helix` with only Haxe, hxcpp and hotreload-hx installed, hot reload in the browser, in CI too from a `haxelib dev` install.
- **Milestone 15: physics, and C libraries in both targets.** 2D arcade physics first (bodies, gravity, move-and-slide against tiles and slopes, deterministic), then Box2D and Jolt as the first two C libraries a game brings (GOALS.md, 4): one way for any C-ABI library, built twice from one pin (WebAssembly for the page, fetched only by a game that uses it; `.a`/`.so` natively), one Haxe API over both, its data crossing in bulk. Box2D (3.x, plain C) proves the way; Jolt (C++) follows behind a C file of its own calls, as libwgf's (no exceptions or RTTI, cross-platform determinism on). The physics study settled the crossing and its cost (`../experiments/haxe/wgf-architecture-experiments/PHYSICS_FINDINGS.md`, 2026-10-09): 32-byte poses read in bulk into a caller-owned typed array, its views rebuilt when the Wasm memory grows, natively straight into Haxe `Bytes`; 10 to 30 ns a body in the browser, 0.023 ms of a 7.5 ms step for Jolt's 1,000 boxes, so the step dominates, not the border. No scratch area shared between calls (librl's: results overwrote each other, views broke on growth; libwgf dropped it). Open from the study, first: the download (Box2D adds 56 KB gzipped, Jolt 248 to 348 KB, against GOALS.md's first goal; each library's addition measured and reported apart from the core), and determinism (the study's own paths matched every byte between browser and native, but libwgf's Jolt build diverged on 1,000 dense boxes, 7,000 floats by up to 7.7 at tick 360; find why before relying on it: build flags, SIMD, the quaternion and matrix round trips). Physics runs off the main thread, the engine and its Wasm in a Web Worker in the browser and on a thread natively, since enough simulation makes that a necessity: the work-off-the-frame module (below). Its interface is asynchronous wherever the work runs, off the thread being the lowest common denominator: a game queues commands and reads the last finished step, interpolated, and on the main thread (a small game, arcade physics, a test) a step's results arrive exactly when they would from a Worker, never sooner, so nothing a game writes depends on where its physics runs, and a replay matches in every mode; fixed steps keep it deterministic. Unmeasured by the study, so measured here first: the Worker's handoff (poses in two buffers transferred back and forth, which any host serves; a SharedArrayBuffer needs cross-origin isolation, which not every host sends) and the step of latency it adds. Behind interfaces, as every system (ARCHITECTURE.md): a contract for each kind (2D, 3D; bodies, shapes, queued commands, the last finished step's poses and contacts in bulk) behind a static service; an adapter per library (`physics2d/box2d/`, `physics3d/jolt/`) holding only what differs by library; arcade physics engine code under the same 2D contract, so a build swaps it for Box2D without the game changing; where the work runs an adapter seam too (Web Worker, native thread), on what the job pools already have, the command buffers, the fixed-step clock and the interpolation the engine's, as a second runner would repeat them; the profile choosing. Also with the racer's lessons (its FRICTION part 2) and a body's drawn transform for the camera. **Done when:** a platformer slice replays alike on both targets; Box2D's and Jolt's replays hash alike in the browser, on Linux and on Windows, each frame, as the trig check does; and a racer slice after libwgf's (`../libwgf-racer`): a vehicle on Jolt, stepped off the main thread on both targets, its poses crossing in bulk, a chase camera on the body's drawn transform, the same lap replayed on both targets.
- **Milestone 16: pathfinding.** Grid A* with flow fields; a navmesh (Recast and Detour, or hxDaedalus, benchmarked first) with steering. **Done when:** agents cross a level in an example on both targets, the same paths.
- **Milestone 17: saves.** A store of the game's own apart from the asset cache: keys to bytes or JSON, slots, a version for migration; IndexedDB in a browser, the user's data directory natively. Begun for the jam (decision 143): `Saves`, text by name, apart from the cache, one operation at a time; slots, versions and a write that survives quitting at once remain. **Done when:** the dressing room saves a look and the services tests cover it on both targets.
- **Milestone 18: sockets and netcode.** `ISocket` (open, send, receive, close) with a browser adapter and a native one with TLS, a shared service reconnecting and queuing; then netcode as a separate package, lockstep over the deterministic pieces, shaped by the final example. **Done when:** two browsers and a native build play the final example together.
- **Fonts: the built-in one only where text is drawn, and the browser's rasterizer.** Measured 2026-10-22: the built-in font's atlas (`generated/fonts`) is some 33 KB gzipped, almost half of the rectangle rung of the size ladder, which draws no text; it becomes an optional part, linked by the first text drawn. Then glyphs drawn in the browser by its own text engine (a canvas's `fillText`, a game's `.ttf` through `FontFace`), as audio and fetch use the browser, behind a rasterizer contract; natively the Haxe TrueType reader and baker stay. The engine keeps the atlas, the layout and the distance field made from the glyphs' bitmaps; kerning by measured pairs; text matching natively closely, not to the pixel (the autopilots' text samples get a tolerance); the default font in the browser the system's sans serif. Prior art read first.
- **Debug switches.** One static (`Debug`), each switch its own, drawn by the engine over the stage and in every view's tree (a view can mute them), toggled from code or, in dev and debug builds, from an on-screen list a key opens: `pickShapes` (what picks test: a hitArea, a kind's own shape, a facing quad, a model's triangles; only what's used, never an approximation), `pickUnderAlphaThreshold` (what picks skip for alpha under the threshold, half), `unpickable`, `drawBounds` (each node's own AABB, what culling uses), `hidden`, `paused`, `frameRate`, `picked` (what's under the pointer, its path and the hit) and `names`. The flag ones draw solid where the node's own flag is set, dashed where it inherits it (so dashed lines in Drawing2D and Drawing3D). PickOverlay2D and PickOverlay3D are the first two as nodes (the user, 2026-10-23).
- **What `paused` freezes, everywhere.** Once everything that moves by itself advances itself (below), `paused` holds all of it still (animators, tweens and timers on the stage included), so "frozen" needs no list (decision 165).
- **One rule for what advances itself.** Some things move on the game's clock by themselves (particles, decals' fading, Tiled's animated tiles, transitions, `Collect2D`, `FullscreenButton2D`); others the game updates by hand (`SpriteAnimator2D`, `Tweens`, `Timers`, `CameraFollow2D`, `FpsOverlay`, `Ui`), and a game that forgets one compiles and does nothing. The rule: what's on the stage, or made for the program, advances itself on `Time.clock`, so it pauses and slows with the game; a game calls `update` only on what it drives itself (a `Ticker`'s simulation, a menu on its own clock), each keeping its `update` for that and a switch to stop advancing itself. An animator with a sprite advances as its sprite is drawn; program-wide `Tweens` and `Timers` run by themselves beside the instances a game keeps for its own clock; `CameraFollow2D` takes a target and a camera; the UI's widgets update on the stage (the user, 2026-10-23, after a review counted the two kinds).

## Deferred until a game needs it

- **Decided after measuring** (milestone 5 left them for numbers that call for them): a spatial index (both culling and picking walk every node; neither earlier framework needed one), visibility and pick masks, skipping the posing of characters out of view (libwgt: 400 models looking away 0.94 ms posed lazily, 16.1 posed; and its trap: culling by last frame's posed box never poses a culled model, so it never walks back into view), occlusion culling, per-instance picks. Also caching skinned poses for picks, if picking many characters is measured to cost.
- **Publishing the haxelib:** waits until the API settles; once it's on lib.haxe.org, sweeping changes are harder to justify (the user, 2026-10-22). Until then games take it by `haxelib git` or `haxelib dev`. The archive will leave out `examples/`, and `init --example` will fetch an example by the installed version's tag (PACKAGING.md).
- **The autopilot's UI:** probes that report which widgets are showing, and events recorded for scripts to wait on, beside `click`.
- **An action bound to a UI widget:** the drawn touch button and the region it presses as one binding, when the UI asks for it.
- **Animation layers:** an upper body's clip over a lower body's.
- **The shader library's next pieces:** an outline of a model's silhouette only, by stencil (the model marks its pixels as it draws, its outline drawn where none is marked: no more draws than today, the stencil beside the depth; stencil state in the pipeline description and every adapter, depth-stencil targets), so a character's eyes, brows and hair don't outline themselves across its face as an inverted hull's parts do, a line inside the silhouette then needing an edge pass on the screen; an outline's width in pixels, held by the distance (world units only today); values of a sprite's own in its vertices, so sprites with one effect but their own flash or palette row share a draw; sprite effects on a stage's text.
- **Morph targets**, and more than four joints a vertex.
- **Examples kept to their feature:** a developer copies an example as a starting point, so each proves one feature and carries little else (the user, 2026-10-22, as the transitions got an example of their own instead of joining `scenes`). Today's decal probes in `sprite2d`, `sprite3d` and `pick` would move to one decals example; milestone 14 makes the examples copyable directories.
- **Indexed reads as read-only arrays:** the `…Count` property and `get…(index)` method pairs (`partCount`/`getPart`, `childCount`/`getChild`, `jointCount`/`getJoint`, `passCount`/`getPass`) as `haxe.ds.ReadOnlyArray` properties, so a game writes `for (pass in model.passes)`; read-only at compile time only (a cast gets past it). A sweep of every pair together, after the jam (the user, 2026-10-22).
- **Projected decals:** a decal shaded onto whatever geometry it falls on (a box projected from the hit, drawn over the surfaces inside it), so it wraps edges and curves instead of lying flat; and on a skinned model one pinned to its triangle and posed with it each frame, creases included. Today's `Decals3D` lies flat on a face, on a skinned model riding the joint weighing most there (decisions 156, 157); the user added this after trying them on the pick example's character (2026-10-22).
- **`ISocket`:** milestone 18.
- **The scene file's next kinds:** a prefab's reference to a node outside itself (an instantiating entry passing a reference down, so a car prefab's behavior could name the race), and the 2D kinds under a `Node2D` root.
- **Timelines:** keyframed tracks per child node (`x`, `y`, `rotation`, `alpha`, `visible`, the sheet frame), labels naming spans, markers the game asks about (`clip.entered("hit")`), played as `SpriteAnimator2D` and `Animator3D` play (glTF's clips are the same shape), saved in the scene file with the nodes they move; authoring wants the scene editor.
- **3D between 2D without post-processing:** a `View3D` drawn into a texture in display order, as one with a chain is now, so 2D drawn before it is under it.
- **2D scene files (`.scene2d`), and screens as scene files:** behaviors on any node, and a helper that loads a scene file and swaps it onto the stage through a transition, so `Splash` and `Loading` become default files with their behaviors.
- **Regional environments:** a model lit by its nearest ancestor's `environment`, several in one view (today one a view: its own, else the first in its tree).
- **Skinning as an optional part of the 3D renderer:** the skinned program, the joint palette and the skinned shadow and pick paths linked only into programs that draw a skinned model, as sprites, text and particles are.
- **Presses for frame-driven screens:** in a fast autopilot (several ticks a frame) each tick ends its presses, so a screen run once a frame (`Splash`, `Loading`, a transition) misses one made in an earlier tick.
- **A test harness publishing after the frame is drawn,** so a snapshot's draw counts are the frame's own.
- **Fixed steps built in:** an app option for the tick rate, a `tick()` override called at it, and the fraction between ticks readable in `update`, so no game makes a `Ticker`.
- **A reference for agents:** from the same doc comments, a symbol index (type, import, one-line purpose, an example) and a file a type, so an agent retrieves `Sprite2D` without the whole package (a review, 2026-10-23).
- **An ECS:** not planned. Milestone 11 settled the game model with behaviors run by a pass (decision 132); an ECS would come only for a game that measures the need.

## Open designs

- **Work off the frame**, to be designed with physics: a module of fixed bulk calls (as the physics study's) that runs on the main thread, in a Web Worker or on a thread behind one asynchronous interface: results arrive as from a Worker wherever it runs, so its callers can't tell. Physics is its main client: a Web Worker with the engine's Wasm in the browser, a thread natively. The environment bake would be its first one-shot client; today environment loads are tied to a per-frame budget, slow at a low frame rate.
- **One frame budget across the job pools:** each pool still delivers under its own 2 ms.
- **macOS: built for in full, verified only as far as a Mac can run it.** macOS is a target like the others: each milestone builds for it, Metal and SDL_GPU included, and CI builds every example there. What waits is verification beyond building: no Mac here can open a HeliX window (the one at hand reaches GL 3.3), so what's claimed is the build, the unit tests, and SDL_GPU on Metal in CI's virtual machine (milestone 8). A real display, gamepads, sound and Retina scaling still need a Mac in hand. iOS waits for a Mac that can run it; Android hasn't been tried.
- **HeliX in webide-hx.** A game on HeliX that writes no shader of its own should need nothing more there, the library's shaders being packed in `generated/` (not tried yet: the library and its dependencies through webide-hx's haxelib mirror). A page can't run sokol-shdc, so a game's own `.glsl` is packed outside it for now; a `.hxshader` is where the two meet, whatever made it. Shaders edited in the page would take sokol-shdc built as WebAssembly (its glslang, SPIRV-Cross and Tint with it) and the packer calling it rather than a process: a probe for webide-hx. Also to look at: what lix does beyond fetching (pinned versions per project, shims), and what HeliX should take from it.
- **The dev loop serving assets where they are.** `tools/example.py dev` copies an asset changed while it runs into the build's assets (2026-10-22: a sheet made again under a running page stayed old, and the code reloaded against it crashed), as it packs shaders there. A plain file needs no step: hotreload-hx's dev server mounting the source directory with the build's over it (packed shaders, manifests) would serve it in place, the manifest still written again as it changes.
- **A WebGPU adapter** would sit beside WebGL2 under the same contracts ([ARCHITECTURE.md](ARCHITECTURE.md)).
